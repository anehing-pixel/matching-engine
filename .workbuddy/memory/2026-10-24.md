## 内存占用实测（mem_probe）

新增 `matching-engine/src/bin/mem_probe.rs`：用 `#[global_allocator]` 包一层计数分配器
（LIVE / PEAK / TOTAL 三个原子量），实测撮合引擎的堆占用，`Cargo.toml` 加 `[[bin]] mem_probe`。

实测数据（release，Windows）：

| 场景 | 合计 | 单条 |
|---|---|---|
| 20,000 个空交易对 | 2.75 MB | 144 B / 交易对 |
| 1 个交易对 × 100 万挂单（一档一单） | 366.25 MB | 384 B / 挂单 |
| 1,000 个交易对 × 1,000 挂单（同样 100 万单） | 365.46 MB | 383 B / 挂单 |
| 1 个交易对 × 100 万挂单（聚成 1 万档，每档 100 单） | 119.39 MB | 125 B / 挂单 |
| 100 万条 Position | 88.64 MB | 92 B / 仓位 |
| 命令级分配抖动（10 万条） | 65.61 MB 累计 | 688 B / 命令 |

单件拆解（各 100 万条）：`VecDeque<RestingOrder>` 本体 58 B/单；`HashMap<u64,(Side,Price)>` 撤单索引 52 B/条；
`BTreeMap<i64,i64>` 价格档骨架 34 B/档（换成 `Level` 值会到 ~73~110 B/档）。

结论：用户数量不是内存变量（`RestingOrder.user_id` 只占 8 B，一个人挂 100 万单与 100 万人各挂 1 单等价）；
空交易对只要 144 B，交易对数量本身也不吃内存。真正的支配项是「挂单条数 × 每单开销」，
而每单开销被「档位碎片化」放大近 3 倍（一档一单 384 B vs 每档 100 单 125 B，差距来自 `VecDeque`
最小容量 4 的 75% 浪费）。交易对数量只通过两条路径间接乘上去：① 每个对的盘口深度（挂单数线性叠加）；
② 清算层 user × symbol 仓位矩阵（当前 `positions` 只按 user_id 建键，跨对会互相覆盖，是待修缺陷）。

验证：`cargo test --release` 19 单元 + 42 集成 = 61 全绿；`cargo clippy --release --bin mem_probe` 无告警。

## 内存探针扩充：三个自变量分离（场景 8/9）

新增两场景，把「品种数」和「人数×品种数」从「挂单数」里剥出来单独计量：

| 自变量 | 实测 | 说明 |
|---|---|---|
| 挂单数 | 384 B/单（一档一单）/ 125 B/单（每档 100 单） | 主项 |
| 品种数 | **9,015 B/对**（≈8.8 KB，主要是 `BufWriter` 默认 8 KB） | 1000 对 = 8.6 MB |
| 用户×品种格 | **107 B/格** | 2 万用户 × 50 品种 = 100 万格 = 102.63 MB |

关键对照：同样 100 万挂单，1 个交易对 366.25 MB vs 1000 个交易对 365.46 MB，差异 <1 MB。
即「品种数本身几乎不占内存」，品种数是通过「每品种盘口深度」间接成为挂单数的乘数。
品种数真正的压力点在 fd 数量 / fsync 队列 / 快照 IO，不在 RAM。

容量公式（写入交付口径）：

```
内存 ≈ 挂单总数 × (125~384 B) + 品种数 × 9 KB + 有仓位的(用户,品种)格数 × 107 B + 用户数 × ~40 B
```

样例：200 品种 × 每品种 2 万挂单 + 50 万用户 × 3 个持仓品种
= 1.2 GB（挂单 86%）+ 1.8 MB（品种 0.1%）+ 160 MB（仓位矩阵 11%）≈ 1.4 GB。

## 场景 10：档位密度扫描（回答「档位多还是单多」）

| 档位数 | 每档单数 | 总内存 | 每单成本 |
|---|---|---|---|
| 1 | 200,000 | 20.25 MB | 106 B |

另：挂单**手数**（`qty: i64`）与内存完全无关，只影响风险敞口。

## 快照方案定位（架构事实）

本引擎是 **STW 快照（第 1 类）**，最简形态：`flush WAL → book.clone() → bincode 整块序列化 → tmp+rename`。

关键：**快照不参与一致性，只用于加速恢复**。WAL 记命令（非事件），正确性由确定性重放保证，
所以快照失败/不做都只影响恢复速度，不影响正确性。`take_snapshot()` 失败时
`cmds_since_snapshot` 不归零，下条命令重试。

排除其他方案的原因（Rust 语境）：fork+COW 在 Windows 不可用且多线程 fork 后 tokio 运行时
与 std 全局锁状态不可靠；持久化数据结构需 im/rpds 依赖且写密集下 Arc 抖动不可接受。
双缓冲是最匹配的升级路径（我们是单线程确定性，增量应用天然确定性），代价是把
「1.4 秒的 2.59× 峰值」换成「24 小时的 2× 常驻」。

## WAL 实现要点 + 两个短板（已写入 docs/03 §2.2）

WAL = **本地磁盘 append-only 文件**，既不是内存也不是 Kafka。帧格式 `[u32 len][u32 crc32][bincode]`，
CRC32 自实现查表版零依赖。三级持久化：BufWriter（不用）/ flush 每次（默认，进程崩不丢断电丢）/
每条 fdatasync（`sync_each`，断电不丢但吞吐锁死）。**WAL 只记命令不记事件**（故与手数无关，恒 66 B）。

**短板一：无 group commit** —— `sync_each=true` 每条命令一次 fdatasync，吞吐被钉死在
1000~10000 TPS，缺失「攒一批一起 sync」的中间档。
**短板二：断电语义未暴露** —— `apply()` 返回 Ok 无法区分「进 OS 页缓存」与「已落盘」，
可能出现「事件已广播但命令丢失」。长期方案是暴露 `synced_seq` 水位（目前不存在）。

## 禁时钟/禁随机数的原因 + seq 实现（含一个真实缺陷修复）

用户问「为什么禁时钟和随机数？在序列怎么做」。核查 `runner.rs` / `wal.rs` / `util.rs` 时
**发现并修复了一个真实缺陷**：

### 缺陷：恢复后 seq 续到 snapshot_seq 而非 WAL 末尾 → 重复重放
- 原代码 `runner.rs: Runner::open` → `seq: recovery.snapshot_seq`。
- 后果：新命令撞用 WAL 里已有的 seq；若此时再做一次快照（last_seq 落在旧记录区间内），
  下次恢复会跳过 `seq <= last_seq` 的记录，但 seq 更大的**旧记录已被算进快照状态**
  却仍满足"seq > last_seq" → **被再重放一遍**。
- 实测复现（临时探针 tests/tmp_seq_probe.rs，已删）：15 单 → 快照 last_seq=5 →
  再挂 10 单崩溃 → 恢复（seq=5，错）→ 挂 3 单 → 快照 last_seq=8 → 二次恢复
  **挂单数 25，期望 18**（7 笔重复）。
- 修复：`RecoveryResult` 新增 `wal_max_seq`（遍历全部 WAL 记录取最大值，含未重放的），
  `Runner::open` 改 `seq: recovery.wal_max_seq`；`recover()` 里把撞号场景写成注释。
- 回归测试：`tests/replay.rs::恢复后seq必须接续到WAL末尾而非快照点`（断言 seq==15、
  二次恢复 18 笔、snapshot_seq==18）。
- 触发条件（运维侧）：崩溃后把 `snapshot_every` 调小再重启，或外部定时器在恢复后
  立刻触发快照 → 已写入 docs/03 §4.1 警告框。
- 另修正措辞：`runner.rs`/`wal.rs` 原写「全局递增 seq」，实际是**每 Runner（每品种）一套
  编号**，Router 下各品种独立从 1 开始；已在 docs/03 新增 §2.3 说明跨品种无全局顺序
  （全局回放/跨品种事务做不到，需在入口层另配 global_seq）。

### 结论要点（供后续复用）
- 禁时钟：时钟不是输入，读钟会让重放结果随时变化；时间改为**入参** `apply(ts, command)`，
  WAL 原样记 ts，因此可复现。快照按命令条数触发（不是定时器）同理。
- 禁随机数：HashMap `RandomState` 每次进程不同（迭代顺序变 → 重放不一致），故核心用
  BTreeMap；order_id 用计数器而非 UUID；冰山抖动用 splitmix64 确定性哈希
  （`util::mix(id, refill_count)`），输入相同输出必然相同。
- 时间优先靠队列插入顺序（VecDeque FIFO），不需要比较时间戳，天然规避"同一微秒谁先"。

验证：`cargo test --release` 19 单元 + 43 集成 = 62 全绿；`cargo clippy --release
--all-targets` 0 warning。

## WAL 写盘代价实测（新增 src/bin/io_bench.rs）

用户问「WAL 是不是内存页复制异步写？先写盘再消费会不会是瓶颈」。写基准实测回答，
并同步进 docs/03 §2.2。

### 实测数字（本机 Windows，N=2 万条命令，release）
| 模式 | 每笔 | 折算 TPS |
|---|---|---|
| 纯撮合不落盘 | 375 ns | 267 万 |
| 撮合 + WAL（只 flush → write 系统调用） | 3.1 µs | 32 万（+8 倍） |
| 撮合 + WAL（每笔 fsync） | 1.07 ms | **935**（+2852 倍） |
| 单次 fsync 裸成本（差分法） | **287 µs** | — |

- **fsync 占落盘成本 99%**；write 系统调用只要 2~3 µs，不是瓶颈。
- 之前 docs/03 里写的"1000~10000 TPS"是估计值，实测 **935 TPS**（本机偏慢，
  NVMe 上约 1 万~10 万，但量级结论不变）。
- group commit 推算（单笔写 2.4 µs + fsync 287 µs / K）：
  K=10 → 3.2 万 TPS；**K=100 → 19 万 TPS（拐点）**；K=1000 → 37 万；K=10000 → 41 万（触顶）。

### 两个概念澄清（已写入 docs/03 §2.2 开头）
1. **数据流**：WAL 是旁路账本，只在崩溃恢复时被读；正常撮合路径是
   「命令 → 同步 write（进 OS 页缓存）→ 立刻内存撮合 → 事件推 Kafka」，不读 WAL。
2. **本项目没有"内存页复制 + 异步写"**（那是 Redis BGSAVE 的 fork+COW，用于快照不是 WAL）。
   WAL = bincode 序列化 → write()，同步、一次一条、无后台线程。
3. **不能简单起线程异步写**：会破坏 apply() 返回 Ok = 已持久化的语义（已 ack 却丢数据 →
   清算记账但簿里没有）。正解是 ring buffer + IO 线程批量 fsync + 撮合线程等自己的 seq 被确认
   （LMAX Disruptor 风格），已在文档中画了示意。

### 度量教训
测 fsync 裸成本不能对"空缓冲区"调 flush——没脏数据时 sync 几乎不花钱，会严重低估
（第一版测出 26 µs，差分法修正后是 287 µs，差 11 倍）。必须用 (写+sync) − (只写) 的差分。

新增 bin：`src/bin/io_bench.rs`（Cargo.toml 加了 [[bin]]）。
验证：`cargo clippy --release --all-targets` 0 warning；`cargo test --release` 62 全绿。

## docs/09 新增 §⑦‑1「两条持久化支柱的边界（WAL 不拷内存页）」

用户追问"WAL 是否复制内存页给快照用"，澄清误解后补文档：WAL 与快照是两条
**相互独立**的持久化支柱，谁也不读对方的运行时内存。
- WAL：只记命令 `{seq,ts,command}`，bincode 序列化后同步 write/fsync，**不碰引擎内存结构、不拷页**。
- 快照：按 `snapshot_every` 命令条数阈值，对**引擎当前状态**全量 clone（STW 同线程），副本来源是引擎、**不是 WAL**。
- 恢复配合：加载最近快照 → 重放 `seq>snapshot_seq` 的 WAL → seq 续到 `wal_max_seq`。
- 新增一张 mermaid 对比图（WAL 增量流 vs 快照全量检查点 + 恢复拼装）+ 维度对照表。
- 强调：真正"拷一份"的动作在快照里（1.4s/2.59× 来源），是主线程同步 STW，非"WAL 拷页交后台写"
  （后者是已排除的双缓冲/fork+COW 升级路径）。

## docs/03 §2.2 新增「sync_each 是启动期只读参数，运行期不可热改（与扩容解耦）」

## 新建 docs/10-订单簿数据结构设计.md

用户问"订单簿 BTreeMap<Price,Level> + VecDeque<RestingOrder> 为什么这么设计、两结构各做什么、优势"，
要求正式写进文档。已新建 `docs/10` 专门文档并补进 README 索引（阅读建议 + 文档清单各加一行）。

文档核心：
- 需求驱动：价格优先（外层有序）+ 时间优先（内层 FIFO）两条硬规则决定"两件套"。
- BTreeMap<Price,Level>（外层）：取最优 O(1) 首元素、定位 O(log n)；**确定性**是选用它的根本
  原因（HashMap 迭代顺序每次进程随机化会破坏重放）；买盘 BidKey 反转 Ord（book.rs:55-60）。
- VecDeque<RestingOrder>（内层）：同价 FIFO，队头出队 O(1) vs Vec 的 O(n)；Level 还聚合
  visible_qty/hidden_qty 供深度行情 O(depth) 直读。
- 引擎层 HashMap<u64,(Side,Price)> 索引（engine.rs:66）：按 order_id O(1) 定位撤单目标，
  内容确定故不破坏重放；与 book 同步，不一致即 panic（engine.rs:455）。
- 为什么不用别的（对照表）：单一 HashMap（无序+非确定）、BTreeMap+Vec（队头 O(n)）、
  LinkedList（缓存差）。
- 与 docs/07 呼应：每挂单=一个 RestingOrder，故挂单数才是内存主项（档位/手数无关）。
- 冰山单可见/隐藏量如何落在结构上 + 关键代码锚点速查表（含行号）。

## engine.rs `index: HashMap<u64, (Side, Price)>` 业务澄清

用户问 `MatchingEngine.index` 是做什么业务的。
- 核查（engine.rs:65-66, cancel:438-457, place 插入:382, 删除:286/354；book.rs remove_from_level:250-266）：

## 设计答疑 + docs/09 §④‑1 新增（后半段对话）

用户连续追问撮合引擎的几个设计选择，逐一澄清（多为概念纠偏，未改代码）：

1. **`impl Default for MatchingEngine` 为什么不直接写 `new`**：当前是 `Default` 持有字段初始化、`new()`/`with_stp()` 都去调它作"唯一真相源"；`with_stp`（engine.rs:112-117）用 `..Self::default()` 只覆盖 `stp_mode`，避免多构造器字段漂移。普通 `fn default()` 也能撑 `..Self::default()`（用户指出"不一定非得是 Default trait"——确实如此，我修正了上一轮措辞），但自定义 trait 会丢掉 `mem::take`/泛型/`#[derive(Default)]` 等 std 生态，且"名叫 default 却不是 Default trait"是反模式；`#[derive(Default)]` 是最精简备选（需 StpMode 标 `#[default]`）。结论：保持 `impl Default` 不动。

2. **`index` HashMap 是否随用户/操作无限膨胀**：纠正"所有下单操作都进 index"的误解。index 只装"当前在簿未成交/未撤的挂单"（仅 Limit/PostOnly 剩余进，市价/IOC 剩余直接取消、全成交/整单拒不进）；离开簿（成交吃光 engine.rs:354 / 撤单 438 / STP 砍单 286）即 remove。体量=单交易对在簿挂单数，按 symbol 分片，与用户数、累计操作数无关；`next_order_id` 只是单计数器不存历史。

3. **撮合"谁看谁 / crossing_price"**：纠正"maker 看 buyer"的误解。是进来的主动单（taker）探对手盘 maker 最优价——买 taker 比 `best_ask`（够得着⇔`p>=best_ask`）、卖 taker 比 `best_bid`（够得着⇔`p<=best_bid`），市价单有货即够得着（book.rs:168-202）。成交价取 **maker 的价**（价格改进），taker 按 maker 价成交不会多付；够不着则本单自己挂成 maker。PostOnly 也先用 crossing_price 探，够得着即整笔拒。
