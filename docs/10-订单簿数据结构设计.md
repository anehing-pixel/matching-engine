# 10 · 订单簿数据结构设计（BTreeMap + VecDeque）

> 对应代码：`matching-engine/src/book.rs`（订单簿本体）+ `src/engine.rs:66`（撤单索引）
>
> 一句话：**订单簿不是一种数据结构，而是一套"两件套"——外层 `BTreeMap` 管"价格优先"，内层 `VecDeque` 管"时间优先"；再加一个引擎层的 `HashMap` 索引管"按单撤单"。三者分工，缺一不可。**

---

## 1 · 需求决定了结构：价格优先 + 时间优先

撮合引擎对订单簿只有两条硬规则（"价格时间优先"）：

1. **价格优先**：买入时，对手卖盘里**报价最低**的先吃；卖出时，对手买盘里**出价最高**的先吃。
2. **时间优先**：同一价格档内，**先挂进来的单先成交**（FIFO）。

这两条规则直接决定了数据结构选型：

- "哪个价格最优"需要**按价格有序查找** → 用有序容器（不能是无序的 `HashMap`）。
- "同价谁先成交"需要**按到达时间排队** → 用队列（不能是无序集合）。

所以订单簿天然是**两层**：外层按价格组织，内层按时间组织。本项目用 `BTreeMap` 做外层、`VecDeque` 做内层，正是为此。

```
OrderBook（订单簿）
  ├── bids: BTreeMap<BidKey, Level>   ← 外层：按价格排序，最优买价排最前
  │      └── Level（某价格档）
  │             └── queue: VecDeque<RestingOrder>  ← 内层：同价按到达时间排队
  └── asks: BTreeMap<Price, Level>    ← 同理
```

> 来源：`book.rs:142-147`（`OrderBook`）、`book.rs:131-138`（`Level`）、`book.rs:74-85`（`RestingOrder`）。

---

## 2 · 外层 BTreeMap<Price, Level>：管"价格优先"

### 2.1 它做什么

- 键是价格（`Price = i64`，定点数，无浮点），值是该价格下的档位 `Level`。
- `best_bid()` / `best_ask()`（`book.rs:155-162`）就是取 `keys().next()`——**最优价永远排在 `BTreeMap` 最前面**，取最优是 O(1) 的迭代器第一步，定位档位是 O(log n)。
- `crossing_price()`（`book.rs:168-197`）：给定主动方方向与限价，直接拿对手盘最优价判断"够不够得着"，决定这一轮撮合是否继续。
- `insert()` / `counter_level_mut()` / `remove_counter_if_empty()`：按价格档增删改。

### 2.2 为什么是 BTreeMap，不是 HashMap

| 维度 | `BTreeMap`（本项目） | `HashMap` |
|---|---|---|
| 是否按 key 有序 | ✅ 永远有序 | ❌ 无序 |
| 取最优价 | `keys().next()`，O(1) 首元素 | 必须遍历全部档位找最值，O(n) |
| 迭代顺序 | 由 key 的 `Ord` 稳定决定 | **每次进程运行都可能不同** |
| 确定性重放 | ✅ 天然支持 | ❌ 会破坏"逐字节一致" |
| 插入/删除 | O(log n) | 平均 O(1) |

**关键原因：确定性。** 本项目是事件溯源 + 崩溃重放模型（见 `docs/09` §⑦），恢复时要把 WAL 的命令重新跑一遍，要求**每一次运行产出完全一样的中间状态**。`HashMap` 的迭代顺序依赖哈希种子，Rust 标准库每次启动都重新随机化（`RandomState`），同一批订单在不同进程里遍历顺序不同 → 撮合结果不同 → 重放对不上。**`BTreeMap` 的顺序只由 key 的 `Ord` 决定，与运行无关，这是它能用的根本原因。**

> 注意：`HashMap` 并非完全禁用——它只用在"按订单 id 点查撤单目标"（`engine.rs:66` 的 `index`），那种场景不需要有序、且 map 内容（id→位置）本身是确定的，不影响重放。真正不能用的，是"用 HashMap 当主价格容器并依赖其迭代顺序"的做法。

### 2.3 买盘为什么要自定义 BidKey（反转 Ord）

`BTreeMap` 默认按 key **从小到大**排。但：

- 卖盘：报价越低越优先 → 升序（`asks: BTreeMap<Price, Level>` 即可，最优卖价=最小价，排最前）。
- 买盘：出价越高越优先 → **需要降序** → 直接存价格不行，于是自定义 `BidKey(pub Price)`（`book.rs:53`），把 `Ord` 比较**反转**（`book.rs:55-60`）：

```rust
impl Ord for BidKey {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        other.0.cmp(&self.0)   // 左右反过来了：BidKey(101) < BidKey(100)
    }
}
```

于是 `bids` 里"价高者排最前"，`best_bid()` 同样用 `keys().next()` 拿到最高买价，和卖盘代码对称。这是 Rust 里"自定义排序"的标准写法，也是本项目少数的"手动实现 trait"点，面试常问。

## 3 · 内层 VecDeque<RestingOrder>：管"时间优先"

### 3.1 它做什么

- 每个 `Level`（`book.rs:131-138`）里有一个 `queue: VecDeque<RestingOrder>`，装的是**同一价格**下所有挂着的单。
- `insert()` 末尾 `level.queue.push_back(order)`（`book.rs:235`）——新单**从队尾入队**，保证"先到先成交"。
- 撮合时从队头 `pop_front()` 取单吃量（`engine.rs` 成交主循环），吃够或档位清空后 `remove_counter_if_empty()` 删空档。
- 撤单 `remove_from_level()`（`book.rs:240-261`）按 `order_id` 在队列里定位并移除（配合引擎层 `index` 先锁定档位，见 §4）。

### 3.2 为什么是 VecDeque，不是 Vec

同价档内要"先进先出"，且**频繁从队头删单**（每成交一笔就吃队头）。

| 维度 | `VecDeque`（本项目） | `Vec` |
|---|---|---|
| `push_back`（新单挂尾） | O(1) | 均摊 O(1) |
| `pop_front`（队头成交） | **O(1)**（双端，不挪元素） | **O(n)**（删头要把后面所有元素前移） |
| 缓存局部性 | 好 | 好 |

若用 `Vec`，每吃一笔队头单都要把档内剩余所有单整体前移一格，档内有 K 张单就 O(K)；高频成交下这是持续的隐性开销。`VecDeque` 的双端特性让队头弹出是常数时间，正好契合"价内 FIFO 出队"的访问模式。

> 选 `VecDeque` 而非 "`LinkedList`"：链表每节点堆分配、缓存差、指针开销大；`VecDeque` 是连续环形缓冲，实际更快，且同样支持 O(1) 双端操作。

### 3.3 Level 还顺手聚合了可见量

`Level` 除了队列，还存 `visible_qty` / `hidden_qty`（`book.rs:132-135`）——这是**该档所有单的可见/隐藏量之和**，挂单/撤单时同步维护（`book.rs:233-234`、`252-253`）。作用：对外发深度行情（`depth()`，`book.rs:266-280`）时**直接读聚合值，不必遍历队列**，O(depth) 而非 O(depth×每档单数)。

## 4 · 引擎层 HashMap<id, (Side, Price)>：管"按单撤单"

订单簿本体只有 BTreeMap + VecDeque，但撤单是"给我一个 order_id，删掉它"——要在哪一侧、哪个价格档？靠遍历全簿找不现实。

于是引擎层维护一份轻量索引（`engine.rs:66`）：

```rust
pub(crate) index: HashMap<u64, (Side, Price)>,   // order_id → (方向, 价格档)
```

- 挂单时写：`engine.rs:383` `self.index.insert(order_id, (req.side, price))`。
- 撤单时查：`cancel()`（`engine.rs:439-446`）先 `index.remove(order_id)` 拿到 `(side, price)`，再调 `book.remove_from_level(side, price, order_id)` 精准定位档位、队列内线性移除。
- **不变量**：`index` 与 `book` 必须同步（成交完/撤完都 `index.remove`，见 `engine.rs:287,355`）；若不一致直接 `panic!` 暴露（"`index 与订单簿不一致`"，`engine.rs:455`），避免"死索引"导致以后撤单 panic。

**为什么这层 HashMap 不破坏确定性**：它的内容是"order_id → 它在簿里的位置"，由命令序列确定性地决定，与 `HashMap` 内部哈希顺序无关；它只是查找辅助，不参与"产生撮合顺序"的迭代。真正决定撮合顺序的 BTreeMap，依然有序。

## 5 · 为什么是"这三件套"，而不是别的

| 候选方案 | 问题 | 本项目选择 |
|---|---|---|
| 单一 `HashMap<Price, Vec>` | 无序 → 取最优要遍历，且迭代顺序非确定 → **破坏重放** | ❌ 不用作主容器 |
| `BTreeMap<Price, Vec>` | 价内用 `Vec`，队头出队 O(n) | 内层换成 `VecDeque` ✅ |
| `BTreeMap<Price, LinkedList>` | 链表缓存差、指针开销大 | 不如 `VecDeque` ✅ |
| 全用 `Vec` 排序 | 插入/取最优 O(n)、且非确定 | ❌ |
| 撤单靠遍历全簿找 id | O(全簿) 太慢 | 引擎层 `HashMap` 索引 O(1) ✅ |

核心取舍一句话：**有序性（BTreeMap）换来了确定性重放能力；双端队列（VecDeque）换来了价内 FIFO 的常数时间出队；HashMap 索引只做"撤单定位"这一件确定性的辅助活。**

## 6 · 与"内存/容量"的呼应（接 docs/07）

`docs/07` 实测过：挂单笔数是内存主项，品种数只是固定开销。从结构看原因很直观：

- 每**一张挂单** = 一个 `RestingOrder`（≈ 5 个 `u64` 字段 + 枚举，几十字节）。
- 每**一个价格档** = 一个 `Level`（聚合 `i64`×2 + 一个 `VecDeque` 头尾指针）。
- 每**一个品种** = 两个 `BTreeMap`（节点开销）+ `VecDeque` 缓冲 + 引擎索引。

所以"挂的单越多 → `RestingOrder` 越多 → `VecDeque` 越长 → 内存越大"，与档位数量、手数（手数只改 `visible` 字段值，不增对象）无关——和 `docs/07` 结论一致。

---

## 7 · 冰山单（可见/隐藏量）如何落在结构上

`RestingOrder` 拆成 `visible` + `hidden`（`book.rs:78-82`），`Level` 也分别聚合（`book.rs:132-135`）：

- 撮合只吃 `visible`；`visible` 吃完但 `hidden > 0` 时 `refill()`（`book.rs:114-126`）从隐藏储备回补显示量，**回补后这单排到队尾**（重排队列，防止长期霸占队首）。
- 深度行情 `depth()`（`book.rs:266-280`）**只输出 `visible_qty`**，隐藏量永不外泄——这是冰山单的意义，也得益于 `Level` 的聚合字段，不必遍历队列区分。
