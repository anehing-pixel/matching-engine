# 03 · 运维手册

> 面向部署与值班的同学。目标是：**出事时能在 5 分钟内找到该做什么**。

---

## 1. 部署形态

### 1.1 进程边界

```text
一个进程 = 一个交易对（推荐）
  ├── matching-engine（Rust，单线程撮合 + WAL + 快照）
  └── 数据目录：/data/<symbol>/{wal, snapshot.bin}

或者：一个进程 = 多个交易对（Router 模式）
  └── /data/{BTC_USDT, ETH_USDT, ...}/...
```

**推荐一个交易对一个进程**，理由：
- 故障隔离：SOL 异常不会影响 BTC；
- 资源隔离：热点交易对可以单独扩容 CPU；
- 恢复更快：只需重放一个交易对的历史。

Router 模式适合交易对很多（几百个）但单个量小的长尾场景。

### 1.2 硬件建议

| 规模 | 撮合机 | 说明 |
|---|---|---|
| 起步（< 1 万用户，< 50 交易对） | 4C8G | 订单簿很小，瓶颈在磁盘 fsync |
| 中等（10 万用户，200 交易对） | 8C16G + NVMe | WAL 写延迟决定吞吐 |
| 大（百万用户） | 按热点交易对拆分到多机 | 单交易对仍然单线程 |

**关键**：一定要用 NVMe SSD。`sync_each=true` 模式下每个命令都要 fdatasync，
SATA SSD 的 fsync 延迟会让吞吐掉一个数量级。

## 2. 配置项

```rust
pub struct PersistConfig {
    pub wal_path: PathBuf,      // 单文件模式=文件路径；滚动模式=目录
    pub snapshot_dir: PathBuf,  // 快照目录
    pub snapshot_every: u64,    // 每 N 条命令做快照
    pub sync_each: bool,        // 每条命令是否 fdatasync
    pub wal_mode: WalMode,      // Single | Rolling { max_segment_bytes }
    pub stp_mode: StpMode,      // None | CancelMaker | CancelTaker
}
```

| 配置 | 生产建议 | 理由 |
|---|---|---|
| `snapshot_every` | 50_000 ~ 100_000 | 太小 → 快照开销占比高；太大 → 恢复时重放慢 |
| `sync_each` | ⚠️ **见 §2.2**，当前实现下无中间档 | `true` 锁死吞吐，`false` 断电丢秒级数据 |
| `wal_mode` | `Rolling { 256 MB }` | 单文件无限增长会拖慢恢复 |
| `stp_mode` | `CancelTaker` | 行业默认；`None` 会被自成交套利 |

### 2.1 参数调优的反直觉点

- **`snapshot_every` 不是越小越好**：快照需要序列化整个订单簿（10 万挂单约几十 MB），
  每 1000 条命令做一次会让 30% 的 CPU 花在序列化上。
- **`sync_each=false` 并不意味着不安全**：进程崩溃不丢数据（已 flush 到 OS），
  只有整机断电会丢最后约 1 秒。资金敏感场景才需要 `true`。

### 2.2 ⚠️ WAL 持久化的两个已知短板（尚未实现，选型前必读）

#### 先澄清一条数据流：WAL 不是"写盘后再读出来消费"

常见误解是把流程想象成 `命令 → 写磁盘 → 从磁盘读出来 → 撮合`。实际不是：

```text
正常运行：  命令 ──①同步 write（进 OS 页缓存）──> 立刻在内存里撮合 ──> 事件推 Kafka
                    └── WAL 只是顺手写一份账本，撮合不读它，也不等它落盘（除非 sync_each）

崩溃恢复：  WAL ──> 顺序读一遍 ──> 重放进内存 ──> 开始服务
```

**WAL 是"只写不读"的账本**，唯一被读的时刻是崩溃恢复。所以"写盘"不参与正常撮合的
数据通路，它是一条旁路。这也是为什么 §4.1 的恢复流程可以把 WAL 当输入重放。

顺带说清另一个概念：**本项目没有"内存页复制后异步写"**。那是 Redis `BGSAVE`
的 fork + COW 思路，用于**快照**（见 ADR 讨论），不是 WAL。我们的 WAL 就是
`bincode 序列化 → write() 系统调用`，同步、一次一条、没有后台线程。

#### 短板一：没有 group commit，`sync_each=true` 会把吞吐钉死

现状在 `wal.rs::WalWriter::append`：

```rust
self.file.flush()?;                       // 每次 append 都推出用户态缓冲
if self.sync_each {
    self.file.get_ref().sync_data()?;     // 每条命令一次 fdatasync
}
```

**每条命令一次 fdatasync**，吞吐被直接钉死。

#### 实测：写盘的代价分两截，真正致命的是第二截

用 `cargo run --release --bin io_bench` 实测（本机 Windows，N=2 万条命令）：

| 模式 | 每笔耗时 | 折算 TPS | 相对纯撮合 |
|---|---|---|---|
| ① 纯撮合（完全不落盘） | **375 ns** | 267 万 | 基线 |
| ② 撮合 + WAL（只 flush，进 OS 页缓存） | **3.1 µs** | 32 万 | **8 倍** |
| ③ 撮合 + WAL（每笔 fsync） | **1.07 ms** | **935** | **2852 倍** |
| ④ 只写 WAL，不含撮合（flush） | 2.4 µs | 42 万 | — |
| ⑤ 单次 fsync 裸成本（差分法） | **287 µs** | — | — |

**结论：fsync 占了全部落盘成本的 99%。** write 系统调用（把数据交给 OS 页缓存）
只要 2~3 µs，完全不是瓶颈；真瓶颈是"强制落盘"这一下。

> 这台的 fsync 是 287 µs，属于偏慢的一档（Windows + 机械盘/杀毒软件扫描都会拖慢）。
> NVMe 上通常能到 10~100 µs，即 ③ 会变成 1 万~10 万 TPS，但**结论不变**：
> 每笔 fsync 比纯撮合慢 2~3 个数量级。

**缺失的是中间档**：

| 持久化级别 | 进程崩溃 | 断电 | 吞吐 | 状态 |
|---|---|---|---|---|
| 留在 `BufWriter` 里 | ❌ 丢 | ❌ 丢 | 最高 | 不使用 |
| `flush()`（默认） | ✅ 不丢 | ❌ 丢 | 高 | ✅ 已有 |
| **group commit**（攒一批一起 sync） | ✅ | ⚠️ 丢最后一批 | **中高** | ❌ **未实现** |
| 每条 `fdatasync` | ✅ | ✅ | **低** | ✅ 已有 |

改造方向：攒 K 条做一次 `sync_data()`，把 fsync 成本摊到一批上。
按实测的 fsync 287 µs、单笔写入 2.4 µs 推算：

| 批量 K | 摊到每笔 | 折算 TPS | 断电丢失窗口 |
|---|---|---|---|
| 1（现状） | 287 µs | 3,461 | 0 |
| 10 | 31 µs | 32,204 | ~10 笔 |
| **100** | **5.3 µs** | **190,000** | ~100 笔 |
| 1,000 | 2.7 µs | 372,531 | ~1000 笔 |
| 10,000 | 2.4 µs | 412,124 | ~1 万笔 |

**K=100 是性价比拐点**：再往上吞吐已经贴着"只写不 sync"的天花板（41 万 TPS），
收益几乎为零，只是把断电丢失窗口白白放大。

**注意**：定时触发只能在 IO 层做（tokio interval），撮合核心禁止读时钟。

#### 为什么不能简单地"起个线程异步写"

有人会想：把 WAL 写盘丢给后台线程，撮合线程不等它直接返回，不就快了？**不行**——
会破坏 `apply()` 的核心语义：**返回 `Ok` 即代表"这笔已持久化"**。

如果不等 IO 线程确认就返回，那么"返回后崩溃"会造成"已 ack 但数据丢失"，
下游清算已经记账、重启后订单簿里却没有这笔 → 账不平。这比慢更严重。

正确做法是 **IO 线程批量写 + 撮合线程等待自己的 seq 被确认**：

```text
撮合线程 ──(ring buffer, 无锁)──> IO 线程 ──> 攒 K 条 write + 一次 fsync
    │                                              │
    └────────── 等待 seq ≤ 自己的 seq 已 sync ─────┘
```

撮合主循环仍然不碰磁盘，fsync 的成本从"每笔一次"变成"每 K 笔一次"。
这也是 LMAX Disruptor 那一类低延迟架构的标准做法。

#### 短板二：断电语义没有对外暴露，调用方看不出差别

`sync_each=false` 时，`apply()` 返回 `Ok` **只代表数据进了 OS 页缓存**：

- 进程崩溃 → ✅ 不丢
- 整机断电 → ❌ 会丢最后约 1 秒

问题在于：**返回值无法区分这两种保证等级**，而下游 Kafka 可能已经把成交事件广播出去了。
极端情况下会出现「清算已经记账、重启后订单簿里却没有这笔成交」。

当前规避方式（二选一）：

1. 资金敏感场景开 `sync_each=true`，接受吞吐损失；
2. 或由上游在收到**下游清算确认**后才认定"已提交"，而不是看 `apply()` 的返回值。

> **长期方案**：实现 group commit 后，暴露一个「已 sync 的最高序号」水位（`synced_seq`），
> 下游只对 `seq <= synced_seq` 的事件做终态处理。这个水位目前不存在。

#### `sync_each` 是启动期只读参数，运行期不可热改（与扩容解耦）

一个容易误判的点：`sync_each` 虽然是 `pub` 字段，但**运行期改不了实际行为**。

- 真正决定是否 `fdatasync` 的是 `WalWriter.sync_each`（`wal.rs:159` 的 `if self.sync_each`），
  它是个普通 `bool`，在 `WalWriter::open(path, cfg.sync_each)`（`wal.rs:136`）时**一次性冻结**。
- 而 `append()` 走的是 `self.sync_each`，**不回读** `PersistConfig.sync_each`。
  `Runner` 内部那份 `PersistConfig` 拷贝虽可改，但 append 流程根本不读它——改它**对落盘行为无影响**
  （这是个「配置拷贝与实际驱动脱节」的小瑕疵，不是特性）。
- 全仓没有任何 setter、`AtomicBool` 或热重载路径。要换值唯一办法是重建 `WalWriter`
  （`drop` 掉重新 `open`），等于把该 `Runner` 重新打开——即**重启该交易对 / 重启进程**，不是热切换。

所以它属于「**启动即定、按交易对各自生效、运行期不可热改**」那一档：

| 维度 | 事实 |
|---|---|
| 来源 | `RouterConfig.sync_each` → 拷贝到每个 symbol 的 `PersistConfig`，启动时生效 |
| 生效时机 | 该 `Runner`（交易对）`open` 时一次性定死 |
| 运行期能否改 | 否。字段 `pub` 但 append 不回读，无热重载 |
| 要改怎么办 | 改配置 + 重启该实例 |
| 是否「扩容才改」 | **否**——它是**持久性 vs 吞吐**的取舍旋钮，不是机器数量旋钮 |

**它和扩容的关系要说准**：改它不是因为机器变多了，而是**业务对该交易对的持久性要求变了**
（例如新接一个监管/资金上要求逐笔落地的品种，就从 `false` 调到 `true`）。
即便要差异化，也只能是每个交易对**各自在启动时**给定不同值（每个 symbol 有独立 `PersistConfig`），
运行中途仍然切不了。

默认值：`RouterConfig::default()` 为 **`false`**（高吞吐，断电可能丢 ~30s 的 WAL）；
演示二进制 `main.rs` 显式设 **`true`**（逐笔断电不丢）。生产按 §2.1 / §2.2 短板二的边界自行取舍。

### 2.3 `seq` 是「每品种一套」编号，不是全站统一编号

`Router` 为每个 symbol 持有独立的 `Runner`，每个 `Runner` 有自己的 `seq` 计数器
（各自从 1 开始）。因此：

- ✅ 同一品种内，`seq` 严格递增、唯一、可当幂等键与对账水位；
- ❌ **跨品种之间不存在可比较的先后顺序**。`BTCUSDT` 的 seq=100 和
  `ETHUSDT` 的 seq=100 没有任何先后关系。

影响：

| 场景 | 是否受影响 |
|---|---|
| 单品种的崩溃恢复、快照、WAL 回收 | ✅ 不受影响 |
| 单品种的下游幂等消费 / 对账 | ✅ 可用 |
| 跨品种的全局时间线回放（"还原某时刻全站状态"） | ❌ **做不到**，需要引入全局 sequencer |
| 跨品种事务（组合单、跨品种风控） | ❌ 做不到 |

若将来需要全局顺序，正确做法是在**入口层**分配一个全局 `global_seq`
（如 Kafka 单分区的 offset），引擎内的 `seq` 仍保持每品种独立——
两者是不同层次的序号，不要把引擎内 seq 当全局序号用。

## 3. 目录结构

```text
/data/
├── BTC_USDT/
│   ├── wal/                     # 滚动模式：wal-000001, wal-000002, ...
│   │   （或单文件模式只有一个 wal 文件）
│   └── snapshots/
│       ├── snapshot.bin
│       └── snapshot.bin.tmp     # 正在写时的临时文件，正常不应残留
└── ETH_USDT/
    └── ...
```

**正常状态检查清单**：

- [ ] 不应存在残留的 `snapshot.bin.tmp`（存在说明上次写快照时被 kill，可安全删除）
- [ ] 段号应连续（`wal-000003` 存在但 `000002` 不存在 = 被 purge 过，正常；
      但 `000002` 存在而 `000001` 缺失且没有快照覆盖 = 异常，需人工核查）
- [ ] `snapshot.bin` 的 mtime 应比 `sync_each=false` 时 WAL 的 mtime 早（快照先落盘）

## 4. 启动与恢复

### 4.1 启动流程（自动）

```text
1. 读 snapshot.bin
   ├── 不存在 → 空簿启动（首次部署）
   ├── 存在但损坏 → 报错退出（不要跳过！需要人工决定是否回退到更早快照）
   └── 存在且 normal → 恢复引擎，记下 last_seq
2. 读 WAL（单文件 or 全部段）
3. 重放 seq > last_seq 的命令
4. 把 seq 续到 WAL 中出现的最大值（wal_max_seq），不是 last_seq
5. 打开 WAL 追加端（滚动模式会先 repair_truncate 最后一段）
6. 开始接收命令
```

> **第 4 步不能省，也不能写成续到 `last_seq`。**
> 曾经的实现就是续到 `last_seq`，会导致新命令撞用 WAL 里已有的 seq，
> 下一次恢复时把已快照包含的旧记录**再重放一遍**，订单凭空翻倍
> （已修复，回归测试：`恢复后seq必须接续到WAL末尾而非快照点`）。
> 触发条件是"快照点落后 WAL 末尾较多"且"恢复后又很快做了一次快照"——
> 例如**崩溃后把 `snapshot_every` 调小再重启**，或外部定时器在恢复后立刻触发快照。
> 这正是 §9.3 要求"外部定时器兜底"时必须注意的顺序问题。

### 4.2 崩溃窗口表（值班必看）

| 崩溃时机 | 数据影响 | 恢复后是否一致 |
|---|---|---|
| 写 WAL 帧写到一半 | 尾部残帧 | ✅ 一致（残帧被忽略，等同该命令未发生） |
| WAL 写完未 flush（用户态缓冲） | 该条丢失 | ✅ 一致 |
| flush 后进程崩 | 数据在 OS 页缓存 | ✅ 一致 |
| `sync_each=false` 且整机断电 | 可能丢最后 ~1 秒 | ✅ 一致（丢的是未确认命令） |
| `sync_each=true` 后断电 | 已 fdatasync | ✅ 保证保留 |
| 快照写到一半（tmp 文件） | 主快照仍是旧的 | ✅ 一致（rename 前旧快照有效） |

**核心结论：任何崩溃都不会导致"半个订单"或"账不平"。**
恢复后状态总等于"某条前缀命令序列的结果"。

> ⚠️ 上表的"一致"指的是**引擎内部状态自洽**，不等于**与外部系统对账一致**。
> 断电场景下可能出现「事件已广播、命令却丢失」，详见 §2.2 短板二。

### 4.3 恢复耗时估算

```text
恢复时间 ≈ 快照加载（与挂单数成正比，10 万挂单约 100~300 ms）
         + WAL 重放（约 1~3 µs/条，10 万条约 0.1~0.3 s）
```

如果恢复超过 10 秒，检查：
1. `snapshot_every` 是否设置过大（WAL 太长）；
2. 磁盘是否太慢（重放是顺序读，慢说明磁盘有问题）；
3. 是否落在"没有快照"的场景（首次启动或快照被删）。

## 5. 故障处置表

| 现象 | 可能原因 | 处置 |
|---|---|---|
| 启动报"快照反序列化失败" | 快照损坏（磁盘错误/版本不匹配） | **不要强行覆盖**。备份现场 → 查是否有旧快照/冷归档 → 若无，从 WAL 全量重放（删除 snapshot.bin，代价是恢复慢） |
| 启动报"WAL 帧损坏" | 尾部半写帧 | 正常现象：`repair_truncate` 会自动处理；若报错在文件中部，说明磁盘故障，需从备份恢复 |
| 撮合卡住无输出 | 死锁（不应发生，引擎单线程）| 抓 CPU profile；看是否卡在 fsync（磁盘坏了会阻塞） |
| 延迟尖刺 p99 飙升 | 磁盘 fsync 变慢 / 快照正在写 / 系统 swap | 看 iostat、看快照时刻是否重合、检查内存是否不足触发 swap |
| 内存持续增长 | 订单簿膨胀（挂单没人撤）/ 隐藏泄漏 | 输出挂单总数指标；检查是否存在下单不撤的做市商 |
| 恢复后账不平 | **严重不变量破坏** | 立即停服，保存 WAL 与快照，用事件流离线重算对账，定位第一个不一致的 seq |
| 目录权限错误 | 换机器/换用户部署 | 检查 `wal` 与 `snapshots` 目录属主 |

### 5.1 应急开关（需产品与风控配合实现）

| 开关 | 作用 |
|---|---|
| 暂停开仓 | 极端行情下只允许平仓，防止风险扩散 |
| 暂停提现 | 发现异常资金流时止血 |
| 只撤单模式 | 停止撮合但允许用户撤单（保护用户，避免"关不掉"） |
| 全站暂停 | 最后手段，需公告 |

> 演练要求：**每个开关上线前必须演练一次**，并记录演练耗时。

## 6. 监控指标与告警阈值

| 指标 | 采集方式 | 告警阈值（建议） |
|---|---|---|
| 命令处理延迟 p99 | 引擎内直方图（见 02 §11） | > 100 µs 持续 1 分钟 |
| 命令处理延迟 p999 | 同上 | > 1 ms 持续 1 分钟 |
| WAL flush 耗时 | 每命令计时 | p99 > 5 ms |
| 快照耗时 | 计时 | > 2 s |
| 恢复耗时 | 启动时记录 | > 10 s |
| 挂单总数 | 引擎统计 | 突增 50% |
| 拒单率 | 按原因计数 | 某原因突增 10 倍（可能是配置错误或攻击） |
| 磁盘剩余 | 系统 | < 20% |
| Kafka 消费 lag | 外部采集 | > 10 万条 |

### 6.1 值得单独盯的两个指标

1. **拒单原因分布**：`PostOnlyWouldCross` 突然暴涨 = 有人在用 PostOnly 试探流动性，
   或者价格带配置错了；`InsufficientLiquidity` 暴涨 = 流动性枯竭前兆。
2. **冰山单占比**：突然升高可能是做市商在隐藏真实意图（也可能是有人在测试系统）。

## 7. 备份与灾备

| 对象 | 频率 | 保留 | 恢复方式 |
|---|---|---|---|
| 快照 | 每次生成后同步到远端 | 最近 3 份 | 直接替换 |
| WAL 段 | 段关闭后上传 | 7 天（+冷归档长期） | 与快照配套使用 |
| 对账快照 | 每日 | 长期 | 审计用 |

**灾备演练要求**：每季度做一次"从零恢复"演练——
在一台干净机器上，只用备份（快照 + WAL）恢复到昨天收盘状态，并核对盘口与昨日终态一致。

## 8. 日常操作

### 8.1 新增交易对

1. 创建目录 `/data/<SYMBOL>/`（Router 模式会自动创建）；
2. 若禁止自动创建（`allow_create=false`），需先调用注册接口；
3. **注意**：新交易对 `next_order_id` 从 1 开始，若下游按 `(symbol, order_id)`
   联合主键则无问题，若只按 `order_id` 唯一则会冲突 —— 部署前确认约定。

### 8.2 重启交易对

```text
1. 停止接收新命令（关闭上游）
2. 等待在途命令处理完（秒级）
3. 触发最后一次快照（可选，减少下次恢复时间）
4. 正常退出（见 02 §12 的顺序）
5. 启动新进程
6. 验证：盘口与停服前一致、拒单率正常
```

### 8.3 磁盘清理

只允许删除：
- `snapshot.bin.tmp`（残留临时文件）
- 已被快照覆盖且已备份到远端的旧 WAL 段

**绝不删除**：最新 `snapshot.bin`、当前正在写的段、未备份的历史段。

## 9. 容量规划参考

> 以下为 **`docs/07-内存与容量规划.md` 的实测值**（`cargo run --release --bin mem_probe`），
> 不再使用估算数字。详细公式、档位密度曲线与快照峰值见 07。

### 9.1 内存

| 数据 | 实测单价 | 10 万挂单时 |
|---|---|---|
| 挂单（内存） | **105 ~ 125 B**（每档 ≥ 4 单，正常盘口）<br>**364 ~ 384 B**（每档 1 单，稀疏盘口） | 12.5 MB（紧簇）<br>**34.8 MB**（碎片化） |
| 档位数（内存） | 34 ~ 110 B/档 | 视行情 |
| 品种固定成本 | **9 KB/对**（含 8 KB `BufWriter` 缓冲） | 1000 个品种仅 8.6 MB |
| 仓位矩阵 | 107 B / (用户, 品种) 格 | — |

> **修正**：旧版写的"10 万挂单约 15 MB"偏乐观。真实值取决于盘口密度：
> 盘口集中在少数档位是 12.5 MB，散成 10 万个价位则是 **34.8 MB（差 2.8 倍）**。
> 容量估算建议按 **300 B/单** 取保守值。

**手数与内存无关**：`qty` 是 `i64` 恒 8 B。挂 1 手和挂 1000 万手占内存一样大。

### 9.2 磁盘与耗时

| 数据 | 实测 |
|---|---|
| WAL 每命令 | **66 B**（只记命令不记事件，与手数无关） |
| 快照文件 | 1 万单 0.85 MB；10 万单 5.74 MB；100 万单 **54.66 MB** |
| **快照耗时** | 1 万单 16.7 ms；10 万单 **121.8 ms**；100 万单 **1.4 s** |
| 快照内存峰值 | **2.59×**（`book.clone()` + 整块序列化缓冲） |

**结论**：内存通常不是瓶颈，**磁盘 fsync 与快照毛刺才是**。
按"每秒 1 万命令"估算，`sync_each=true` 需要撑住 1 万次 fdatasync/秒 ——
NVMe 约 1~3 万 IOPS 勉强够，SATA SSD（500~2000）直接崩。**这也是 §2.2 短板一的由来。**

### 9.3 快照间隔怎么定

`snapshot_every` 本质是在两个成本之间定价：

```text
间隔小 → 快照频繁 → 每次 121.8 ms（10 万单）停摆，但重启重放少
间隔大 → 毛刺少     → 但重启要重放几十万条 WAL
```

两个必须知道的约束：

1. **挂单量大的品种必须调小阈值**：100 万挂单一次快照要停摆 1.4 秒；
2. **低流量品种必须配外部定时器兜底**：它可能几天都攒不够 `snapshot_every` 条命令，
   导致 WAL 永不回收、重启重放极慢。`take_snapshot()` 已是 `pub`，可在 IO 层用
   tokio interval 调用（撮合核心自身禁止读时钟，所以触发条件是"命令条数"而非时间）。

> 附带好处：按命令条数触发**天然让各品种错峰**。若改用统一定时器，
> 所有品种会在同一秒一起做快照，内存峰值叠加、全站同时停摆。
