# 01 · 撮合引擎设计与实现

> 说明**已经做出来的东西**是怎么设计、怎么运作的。
> 未实现功能见 `02-未实现功能设计规格.md`。

---

## 1. 一句话架构

> **一个交易对一个撮合进程，纯内存订单簿，先写日志后计算，事件流向外部。**

```text
                    ┌──────────────────────────────────────────┐
   外部命令          │            Runner（持久化编排）             │
（Kafka / API）      │                                          │
        │           │  ① 分配 seq                               │
        ▼           │  ② 写 WAL（先落盘！）                       │
  Command ──────────▶│  ③ 调用引擎 process()  ← 纯内存、同步、单线程 │
                    │  ④ 达到阈值 → 做快照                        │
                    │  ⑤ 返回 Vec<Event>                        │
                    └───────────────┬──────────────────────────┘
                                    │ Events
                                    ▼
                        Kafka（下游：清算 / 行情 / 审计）
```

关键设计取舍：**撮合与持久化分离**。引擎不知道磁盘存在，Runner 不知道撮合规则。
这样引擎可以被单测穷举，持久化可以被替换（单文件 → 滚动段）。

|---|---|---|---|---|

## 3. 数据结构为什么这么选

### 3.1 订单簿：`BTreeMap<Price, Level>` + `VecDeque<RestingOrder>`

| 选项 | 为什么不用 |
|---|---|
| `HashMap<Price, Level>` | 撮合需要"最优价"，HashMap 要每次遍历找最值，O(n)；且迭代顺序不确定，破坏确定性 |
| `Vec<(Price, Level)>` 排序数组 | 插入 O(n)，撤单 O(n)，档位多时退化 |
| 二叉堆 | 只能取最值，撤单（任意位置删除）困难 |
| **BTreeMap** | 有序、插入/删除 O(log n)、迭代顺序确定 —— 三项全中 |

档内用 `VecDeque` 而不是 `Vec`：FIFO 只需 `push_back` / `pop_front`，`VecDeque` 两者都是 O(1)，`Vec` 的 `remove(0)` 是 O(n)。

### 3.2 买盘为什么要 `BidKey`

`BTreeMap` 只能升序迭代。卖盘"价格低的优先"天然满足；买盘要"价格高的优先"，
于是包一层 `BidKey`，把 `Ord` 反过来：

```rust
impl Ord for BidKey {
    fn cmp(&self, other: &Self) -> Ordering {
        other.0.cmp(&self.0)   // 注意是 other 先 —— 这就是"反转"
    }
}
```

**为什么不存负价格**（`bids: BTreeMap<i64, Level>` 用 `-price` 做 key）？
也能work，但会让"从盘口读出价格"时到处出现 `-` 号，极易漏掉一个负号导致逻辑错。
类型包装让"反转"这件事只存在于一处。

### 3.3 冰山单的 visible / hidden 双量

```rust
pub struct RestingOrder {
    pub visible: Qty,        // 摆在队列里、能被吃、会计入深度
    pub hidden:  Qty,        // 藏着、不计入深度、吃完后回补
    pub display_qty: Option<Qty>, // 每次回补多少
}
```

档位维护两个汇总：`visible_qty`（对外展示）与 `hidden_qty`（仅统计）。
**深度只暴露 visible**，这是冰山单的全部意义。

## 4. 撮合主循环（本项目的核心 40 行）

```rust
while remaining > 0 {
    // 步骤 1：对手盘最优价够不够得着？
    let Some(level_price) = self.book.crossing_price(req.side, req.kind, req.price) else {
        break;
    };
    let level = self.book.counter_level_mut(req.side, level_price);

    while remaining > 0 && !level.queue.is_empty() {
        // 步骤 2：取队首（价格时间优先的"时间优先"就体现在这里）
        let (front_id, front_user, front_visible) = { /* 取只读快照 */ };

        // 步骤 3：自成交防护（可选）
        // 步骤 4：按 min(taker 剩余, maker 可见量) 成交，写 Trade 事件
        // 步骤 5：队首吃完 → 普通单出队 / 冰山单回补并排到队尾
    }
    // 档位空了就删掉
}
```

### 4.1 为什么"取只读快照再操作"

Rust 的借用规则不允许同时对 `level.queue.front()` 持有可变借用再做 `level.visible_qty -= x`。
我们的做法是：先用不可变借用把需要的三个值 `copy` 出来（`u64`/`i64` 都是 `Copy`，零成本），
再开一个短小的可变借用块完成修改。**这是 Rust 里处理"读-改"的常用手法**，
比 `RefCell` 或拆结构体都更清晰。

### 4.2 成交价永远用 maker 的价格

```rust
price: level_price,   // 挂单方（maker）的价格
```

这是行业铁律：**被动方定价**。如果按 taker 的限价成交，一个"限价 100 买、卖盘只要 90"
的人就会以 100 成交，白送钱给对手。

### 4.3 冰山单回补为什么排到队尾

如果回补后仍在队首，一个大冰山单可以长期霸占"时间优先"位置，
其他同价订单永远排在它后面 —— 等于用冰山单实现了队列插队。
所以回补 = 重新排队（`pop_front` → `refill` → `push_back`）。

## 5. 订单类型语义总表（实现必须与表一致）

| 类型 | TIF | 会立即成交时 | 剩余部分 | 备注 |
|---|---|---|---|---|
| Limit | Gtc | 成交 | 挂簿 | 默认类型 |
| Limit | Ioc | 成交 | 取消（`CancelReason::Remainder`） | 只吃一次流动性 |
| Limit | Fok | 成交 | —（前置检查：不足则**整单拒绝**） | 见 5.1 |
| Market | — | 成交 | 取消 | 无价格保护 |
| PostOnly | — | **整单拒绝**（`PostOnlyWouldCross`） | — | 只做 maker |
| 任意挂簿类型 + iceberg | — | 成交 | 挂簿（visible/hidden 拆分） | 深度只见 visible |

### 5.1 FOK 为什么必须前置检查

如果边吃边判断，可能出现"吃到一半发现流动性不够"的状态——
单子已经部分成交，无法回滚（事件已发出）。
所以 FOK 在处理前先扫一遍对手盘**可见量**（不含量化隐藏量）：

```rust
if req.kind == OrderKind::Limit && req.tif == TimeInForce::Fok
    && self.available_liquidity(req.side, req.price) < req.qty { 拒绝 }
```

### 5.2 每个 order_id 恰好一个终态事件

| 终态事件 | 含义 |
|---|---|
| `Placed { remaining }` | 挂簿（`remaining > 0`）或全成（`remaining == 0`） |
| `Canceled { reason }` | 剩余被取消 / STP 取消 / 主动撤单 |
| `Rejected { reason }` | 未进入撮合（参数非法、PostOnly 交叉、FOK 不足、撤单找不到） |

这条不变量让下游结算不需要处理歧义：**看到终态就可以结账**。

## 6. 事件模型

```rust
pub enum Event {
    Rejected { order_id, reason },
    Placed { order_id, remaining },
    Trade { maker_order_id, maker_user_id,
            taker_order_id, taker_user_id,
            price, qty, taker_side },
    Canceled { order_id, reason },
    DepthSnapshot { bids, asks },   // 每条命令末尾附一份前 10 档
}
```

设计要点：

1. **一条命令 → 0..N 个事件**，顺序即下游处理顺序。
2. **`DepthSnapshot` 放在末尾**：下游可以先处理 Trade 更新账本，再用快照校正行情视图；
   如果快照放前面，会出现"快照与成交对不上"的瞬时状态。
3. **事件里带 user_id**：清算方不必回查订单表，省一次 IO，也避免"订单表还没写完"的竞态。
4. **事件是账本的唯一依据**：撮合引擎不记账，账本由下游按事件流构建（事件溯源）。

## 7. 持久化设计

### 7.1 WAL 帧格式

```text
┌────────────┬────────────┬──────────────────────┐
│ len (u32)  │ crc32(u32) │ payload (bincode)    │
│ 4 字节      │ 4 字节      │ len 字节              │
└────────────┴────────────┴──────────────────────┘
```

- `len` 让读端能按帧跳读，坏一帧不至于整文件报废；
- `crc32` 能发现"写了一半"和"磁盘位翻转"；
- 自实现 CRC32（查表，约 25 行）而不引依赖，减少供应链面。

**崩溃窗口表**（这是理解持久化的关键）：

| 崩溃时机 | 数据状态 | 恢复结果 |
|---|---|---|
| `append` 写入了长度头就崩 | 残帧，读到即停 | 该记录视为未发生（安全） |
| `append` 写完但未 flush | 数据在用户态缓冲，丢失 | 同上（安全） |
| `flush` 到 OS 后进程崩 | 数据在页缓存，仍在 | 记录保留 |
| `flush` 后整机断电（`sync_each=false`） | 可能丢失尾部 | 同上（丢失即未发生，一致） |
| `sync_each=true` 后断电 | 已 fdatasync | 记录保证保留 |

> 所有情形都满足同一性质：**恢复后的状态 = 某条前缀命令序列的结果**，永远不会出现"半个订单"。

### 7.2 快照

- 原子写入：`snapshot.bin.tmp` → `rename` 成 `snapshot.bin`（rename 是原子操作）。
- 内容：`last_seq` + `next_order_id` + 订单簿 + 撤单索引 + `stp_mode`。
- **顺序**：先 `wal.flush()` 再写快照 —— 保证"快照覆盖的 seq 之前的数据必然已落盘"。

### 7.3 恢复流程

```text
加载 snapshot.bin
   ├── 有 → 用快照恢复引擎，记下 snapshot_seq
   └── 无 → 空引擎，snapshot_seq = 0
读 WAL（单文件 或 全部滚动段，按段号升序）
   └── 逐条：seq <= snapshot_seq ? 跳过 : 重放到引擎
```

测试保证（`tests/replay.rs`）：

- `崩溃恢复_快照加WAL重放与全程执行结果一致`：重放事件与"实时执行的尾部事件"**逐条相等**，
  且盘口与纯内存基准完全一致。

### 7.4 滚动分段

- 段号 `wal-000001`，写到 `max_segment_bytes` 切下一段；
- 快照后 `purge_below(current_index)` 删除当前段之前的所有段；
- 打开时对最后一段做 `repair_truncate`，把半写帧截掉再追加。

## 8. 确定性纪律（违反任何一条都会破坏重放）

| 规则 | 原因 | 检查方式 |
|---|---|---|
| 禁用浮点，金额一律 i64 最小单位 | 浮点误差会累积，重放结果漂移 | code review + 后续可加 clippy lint |
| 不使用系统时间/随机数 | 换台机器结果不同 | 引擎接口不接收时间；`ts` 由调用方随记录传入 |
| 不依赖 HashMap 迭代顺序 | HashMap 顺序随机化 | HashMap 只用于按 id 点查，不遍历输出 |
| 不使用并发 | 调度顺序不确定 | 引擎方法均 `&mut self`，单线程调用 |
| 排序必须全序（含 tie-break） | 相等元素顺序不定 | ADL 排序用 `(盈亏 desc, user_id asc)` |
| 崩溃恢复只重放"输入" | 输出由输入确定性推导 | WAL 存 `Command` 而非 `Event` |

**验证方式**：`重放确定性_相同输入必然相同输出` —— 2000 条随机命令跑两遍，比较完整事件序列与盘口。

## 9. 合约清算

### 9.1 核心指标

```text
权益 equity   = 保证金 margin + 未实现盈亏 pnl
名义价值 notional = 仓位 size × 标记价格
保证金率 ratio = equity / notional      （内部用万分之一整数表示，避免浮点）
强平条件 ratio < 维持保证金率 mmr
```

### 9.2 标记价格 vs 最新成交价

**必须用标记价格**（外部指数加权或本所价格限幅合成）。
用最新成交价会被"插针"操纵：砸一笔小单把价格瞬间打低，就能扫掉一片正常仓位。

### 9.3 强平结算三步

```text
① realized_pnl = (fill_price - entry) × size × (多 ? 1 : -1)
② fee = fill_price × size × liq_fee_bp / 10000
③ leftover = margin + realized_pnl - fee
     leftover < 0  → 缺口：先扣保险基金，不足部分记 socialized_loss（待 ADL）
     leftover >= 0 → 余额进保险基金
```

### 9.4 ADL 排序（确定、可解释）

1. 只挑"与穿仓方向相反、且当前盈利"的仓位；
2. 按**未实现盈亏降序**（赚得多的先让出）；
3. 盈亏相同 → 按 `user_id` 升序（tie-break，保证任何机器结果一致）。

## 10. 性能特征

| 度量 | 实测（本机 release） | 说明 |
|---|---|---|
| 1 万笔纯挂单 | ~5.6 ms | 约 0.56 µs/笔，主要是 BTreeMap 插入 |
| 1000 档簿 + 1000 次吃单 | ~826 µs | 约 0.8 µs/笔，含深度快照生成 |
| 混合负载 1000 次（含撤单） | ~559 µs | 约 0.56 µs/笔 |

为什么能做到微秒级：

1. 纯内存，无系统调用（WAL 是批量/异步的边界，不在撮合循环内）；
2. 无锁（每交易对单线程，实例间零共享）；
3. 无 GC（Rust 无运行时回收，延迟分布平坦）。

优化空间（尚未做）：`VecDeque` 与 `Vec<Event>` 的动态分配可以用 arena / 池化消除。

## 11. 错误与 panic 策略

| 场景 | 策略 |
|---|---|
| 用户输入非法（数量 ≤ 0、市价带价） | `Event::Rejected`，**不 panic** |
| 撤单找不到 | `Rejected { UnknownOrder }`，不 panic |
| WAL 读写 IO 错误 | 向上返回 `io::Result`，**宁可停机也不允许未落盘就执行** |
| index 与订单簿不一致 | **panic** —— 属于内部不变量破坏，静默继续会产生错账 |
| WAL 帧损坏 | 视为尾部截断，`Ok(None)` 停止迭代；由 `repair_truncate` 修复后继续 |

原则：**用户错误用事件，系统错误用 Result，不变量破坏用 panic**。

## 12. 已知限制（不是 bug，是有意为之）

1. 引擎只服务一个交易对（多交易对靠 `Router`）；
2. 单机、单线程、无副本（高可用需外部做"快速恢复"而非双活）；
3. 只有一种保证金模式、单一维持保证金率（见 `02` 的补齐规格）；
4. 无资金费率、无条件单；
5. 深度快照每命令生成一次，高频时是主要输出体积来源（可改为增量）。

## 13. 术语表

| 术语 | 含义 |
|---|---|
| maker | 挂单方，被动成交，提供流动性 |
| taker | 主动方，吃掉别人的挂单 |
| 价格时间优先 | 先比价格优劣，同价时先到先得 |
| STP | Self-Trade Prevention，自成交防护 |
| GTC / IOC / FOK | 一直有效 / 立即成交否则取消 / 全成或全不成 |
| PostOnly | 只允许做 maker，会立即成交就拒绝 |
| 冰山单 | 只显示部分数量的挂单 |
| 标记价格 | 用于计算盈亏与强平的"公允价"，非最新成交价 |
| 维持保证金率 | 触发强平的最低保证金率 |
| 穿仓 | 亏损超过全部保证金，权益为负 |
| 保险基金 | 穿仓时垫付用的公共资金池 |
| ADL | Auto-Deleveraging，从盈利对手方强制减仓分摊亏损 |
| 事件溯源 | 以不可变事件流作为唯一真相，状态由重放推导 |
| CQRS | 读写分离，撮合只写事件，查询走独立读模型 |
