## F-01 资金费率结算

**实现**：`ClearingHouse::settle_funding()` / `preview_funding()`。

**关键设计**：
- 幂等键 `(symbol, settle_ts)`，用 `BTreeSet` 记录已结算期次 → 重复调用返回空列表；
- 逐仓从 `Position.margin` 扣减/增加，全仓从 `Account.cash` 扣减/增加；
- **允许保证金变为负数**（不砍到 0）——砍到 0 等于凭空免除债务，应由强平流程处理；
- 整数取整导致的"多空不守恒"差额累加进保险基金。

**已知限制**：
- 未实现"结算期间冻结开平仓"的状态机（当前依赖单线程串行，若接入 Kafka 需在调度层保证）；
- 费率由外部传入（不自己从基差计算）。

## F-02 多档维持保证金表

**实现**：`TierTable::maintenance_margin(notional)` / `initial_margin(notional)`。

**关键设计**：**阶梯式累加**而非整体套用。50000 名义价值在标准表下 = 前 1 万 × 0.5% + 后 4 万 × 1% = 450，而不是 50000 × 1% = 500。
构造时校验 `max_notional` 严格递增，避免配置错误。

**已知限制**：`TierTable::standard()` 是写死的示例表，生产需从配置加载（加载函数未做）。

---

## F-05 逐仓 / 全仓保证金模式

**实现**：`Position.margin_mode` + `ClearingHouse.accounts`。

**关键设计**：
- 逐仓：`equity = margin + pnl`，与 `maintenance_margin(该仓位)` 比较；
- 全仓：`equity = cash + Σpnl`，与 `Σmaintenance_margin` 比较，触发时**清掉该用户全部全仓仓位**；
- 扫描顺序：先逐仓（user_id 升序）后全仓（user_id 升序）——风险隔离优先。

**已知限制（重要）**：
- 当前模型**每个用户只保留一个净仓位**（`BTreeMap<user_id, Position>`），因此"同一用户在不同交易对的多个全仓仓位互相抵扣"无法演示；真实系统需要 `BTreeMap<(user_id, symbol), Position>`。这是数据结构层面的下一步改造，接口已按此方向设计（`cross_equity` 已按"遍历该用户所有全仓仓位"实现，改成多 symbol 只需改 key）。
- 有仓位时禁止切换模式（校验未实现，由 API 层保证）。

## F-06 ADL 完整规则

**实现**：`ClearingHouse::plan_adl()`（含坏账/退款）与 `compute_adl()`（只要明细）。

**关键设计（一处重要的公式修正）**：
设计稿里写的是 `score = 收益率 / 杠杆`，实现时发现把 margin 约掉后等价于 `pnl / notional`——
对同一开仓价、同一标记价的仓位，这个值**恒定相同**（等于价格涨跌幅），完全失去区分度。
所以改成**三级排序**：

```text
收益率 (pnl/margin) 降序 → 杠杆 (notional/margin) 降序 → user_id 升序
```

这既保留了"赚得最多的先减"的直觉，又保证全序确定。

**分摊与取整**：按贡献向上取整到最小数量单位，多扣的记 `refund`；所有候选不足时记 `bad_debt`（必须告警）。

**已知限制**：
- 未做"跨用户净额"（同一用户在该合约只一个净仓位，天然满足）；
- 未与强平并发做互斥标记（当前单线程下不会并发）；
- 未实现"通知被 ADL 用户"。

## F-07 报价保护

**实现**：`PriceBand` + `MatchingEngine::set_price_band/set_mark_price`。

**关键设计**：
- 基准价是**标记价格**（不是最新成交价，否则可被插针操纵）；
- 两种策略：`Reject`（直接拒单）/ `Clamp`（把价格夹到边界后继续）；
- 未收到标记价格（`mark_price == 0`）时**不检查**，避免启动阶段全部拒单；
- 配置随快照持久化，重启不失效。

**已知限制**：
- 只检查限价单的显式价格；市价单不做隐含价格检查（需要额外定义"市价可接受滑点"）；
- 未实现"极端行情临时扩大区间"的联动。

## F-08 批量接口

**实现**：`Command::Batch { cancel_order_ids, new_orders }`，输出 `Event::Batch(Vec<Event>)`。

**关键设计**：**两遍扫描**——第一遍只做静态校验（撤单目标存在、参数合法、价格带通过），任一失败整批拒绝且**状态完全不变**；第二遍执行时不会再失败，因此天然原子。

**已知限制**：不做依赖执行顺序的动态校验（如批内 PostOnly 是否会被批内前面的订单撮合），成本高于收益，已在文档中写明取舍。

---

## F-09 费率标识

**实现**：`Event::Trade` 新增 `maker_fee_class` / `taker_fee_class`（`FeeClass::{Maker, Taker}`）。

**关键设计**：引擎**只输出角色，不算金额**。费率依赖 VIP 等级、30 日交易量等账户侧数据，放进引擎会让状态膨胀、快照变大、费率调整还要改引擎。

**验证方式**：可 grep 引擎代码确认不含任何费率数值（`liq_fee_bp` 属于清算模块，不在引擎内）。

---

## F-10 冰山单随机化

**实现**：`RestingOrder.refill_count` + `util::jitter(base, seed, jitter_bp)`。

**关键设计**：
- 种子 = `mix(order_id, refill_count)`，两者都确定 → **同一订单同一次回补永远相同结果**，重放仍逐字节一致；
- `jitter_bp = 0` 时完全退化为固定显示量（向后兼容）；
- 抖动范围受 `[1, base×2]` 约束，防止极端值。

**已知限制**：抖动是"均匀分布"，真实做市商可能希望更接近对数均匀；当前实现优先保证简单与可解释。

## F-11 指标埋点

**实现**：`metrics::Histogram`（24 个 2 的幂桶）+ `metrics::Metrics`。

**关键设计**：
- 固定内存（24 × u64），永不上涨；
- `observe()` 只做几次数组自增，路径上无 IO、无锁；
- 指标包括：命令数、事件数、成交数、按原因分类的拒单数、延迟 p50/p99/p999、挂单总数；
- `Runner::apply` 内用 `Instant` 测量耗时——**只测量不存储**，不影响状态确定性。

**已知限制**：直方图桶精度是 2 倍（误差较大但足够看趋势）；导出方式是"取一行 JSON"，未做 HTTP 端口/推送。

## F-12 优雅关闭

**实现**：`Runner::graceful_shutdown()`。

**关键设计**：
```text
1. 置 shutting_down 标记（此后 apply 返回 Err）
2. take_snapshot()（内部先 wal.flush() 再写快照）
3. 返回；调用方提交 Kafka offset 后退出
```
顺序不可颠倒：快照必须在 flush 之后，否则会出现"快照声称覆盖的 seq 其实没落盘"。

**已知限制**：未处理操作系统信号（SIGTERM 绑定在 main/服务层做，库不耦合进程控制）。

## F-13 快照迁移 + 冷归档

**实现**：`snapshot::SnapshotEnvelope` + `SnapshotV1` 迁移；`archive::archive_segments()`。

**快照版本策略**：
```text
version == 2 (CURRENT)  → 直接解析
version == 1            → 按旧结构解析 + migrate_v1（新增字段给默认值）
version > 2             → 明确报错，拒绝降级运行
无信封（极旧文件）        → 当 v1 解析
```

**冷归档**：
- 把段号小于 `keep_from` 的段复制到冷目录（**不删源文件**，删除由调用方决定）；
- 生成 `manifest.tsv`（段号、起止 seq、字节数、CRC32），可直接用 Excel/less 查看；
- `find_by_seq(seq)` 定位段，`verify_entry` 重算 CRC 校验完整性；
- **不做压缩**（保持零依赖），压缩点已在注释中标明。

**已知限制**：清单是 TSV 手写格式，字段增加时需兼容处理；未实现"直接按 seq 从冷存回放"的一站式 API。

## 未实现说明（F-03 / F-04）

这两项**故意没有实现**，原因不同：

### F-03 条件单

不是难度问题，而是**依赖关系没打通**：条件单需要"行情驱动的时间轴"
（价格更新 → 扫描触发器 → 生成订单），而当前架构里引擎是被动接收命令的，
没有"持续喂价格"的驱动层。正确做法是：

1. 新增 `TriggerBook`（`BTreeMap<(Price, u64), TriggerOrder>`），并入快照；
2. 由行情服务在每次价格更新时调用 `trigger_book.on_price(new_price)`；
3. 输出 `Vec<Command>` 交给 `Runner::apply`。

**在把行情驱动接进来之前实现它，只会得到一个"永远不触发"的死代码**，所以留到接入行情时一起做。
详细规格见 `02` §3（含跳空穿越、触发顺序等关键设计）。

### F-04 proptest 属性测试

需要引入 `proptest` 依赖（当前 dev-dependencies 只有 criterion）。
现在已有 61 个测试覆盖主要语义，属性测试的价值是"发现未知组合的 bug"，
建议在下一步与其他功能一起引入，避免每次都多编译一个依赖树。
