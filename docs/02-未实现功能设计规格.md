# §1 F-01 资金费率结算（P0）

## 1.1 业务背景

永续合约没有到期日，靠**资金费率**把合约价格锚定到现货指数：

- 合约价格 > 现货 → 资金费率为正 → 多头付钱给空头（抑制做多）；
- 合约价格 < 现货 → 费率为负 → 空头付钱给多头。

每 8 小时结算一次（00:00 / 08:00 / 16:00 UTC）。**这是永续合约的价格锚，缺了它合约机制不成立**，所以是 P0。

## 1.2 现状

完全没有实现。`ClearingHouse` 只处理成交与强平。

## 1.3 数据模型

```rust
/// 一次资金费率结算的参数
pub struct FundingRound {
    pub symbol: String,
    /// 本期费率（万分之一，正=多头付，负=空头付）
    pub rate_bp: i64,
    /// 结算使用的价格（通常取结算时刻的标记价格）
    pub mark_price: Price,
    /// 结算时间戳（由外部调度器传入，引擎不读时钟）
    pub settle_ts: u64,
}

/// 单个用户的结算结果（事件）
pub struct FundingSettled {
    pub user_id: u64,
    /// 实际支付金额：正=支出，负=收入
    pub amount: Price,
}
```

## 1.4 算法步骤

```text
1. 冻结开平仓（可选但推荐）：进入 SETTLING 状态，拒绝新开仓单
2. 快照所有仓位（按 user_id 升序，确定性）
3. 对每个仓位：
     notional = size × mark_price
     raw      = notional × rate_bp / 10000
     amount   = 多仓 ? +raw : -raw      // 多头付钱为正
4. 校验守恒：Σamount == 0（允许因整数取整产生 1 单位误差，误差进保险基金）
5. 逐户扣/加保证金；保证金不足者 → 追加保证金不足标记，交由强平引擎处理
6. 输出 FundingSettled 事件流 + 汇总（总金额、参与户数）
7. 解除冻结
```

## 1.5 边界与坑

| 坑 | 处理 |
|---|---|
| **整数取整导致不守恒** | `Σamount` 允许 ±N 单位误差（N = 用户数），差额记入保险基金，并在事件里标明 |
| **结算期间有成交** | 必须冻结（步骤 1）或在单线程中排队，否则"用哪个价格算 notional"会有歧义 |
| **保证金被扣成负数** | 不要直接砍到 0：保留负值并标记 `needs_liquidation`，交由强平流程统一处理 |
| **空仓跨过结算时刻** | 结算那一刻的持仓才付/收，之后开仓不补缴 |
| **费率极端值** | 配置上限（如 ±0.75%/8h），防异常输入 |
| **幂等** | 以 `(symbol, settle_ts)` 为幂等键，同一期只能结算一次 |

## 1.6 接口草案

```rust
impl ClearingHouse {
    /// 执行一期资金费率结算；返回每户结果。
    pub fn settle_funding(&mut self, round: &FundingRound) -> Vec<FundingSettled>;

    /// 只计算不落地（用于预览/对账）。
    pub fn preview_funding(&self, round: &FundingRound) -> Vec<FundingSettled>;
}
```

## 1.7 验收标准

1. 多空持仓相等、费率为正时：**多头支出总额 == 空头收入总额**（±取整误差）；
2. 同一 `settle_ts` 重复调用第二次返回空（幂等）；
3. 结算前后，所有用户 `保证金 + 未实现盈亏` 的总和变化量 == 0 + 取整误差；
4. 保证金被扣成负的用户，在随后的强平扫描中被扫出。

# §2 F-02 多档维持保证金表（P0）

## 2.1 业务背景

真实交易所按**仓位名义价值分档**设置维持保证金率：仓位越大，要求越高。
理由：大仓位平仓时对市场冲击大，清算风险更高，必须留更多缓冲。

用单一比例的问题：一个 100 万 USDT 的仓位和一个 1000 USDT 的仓位用同样的 0.5%，
大仓位在剧烈行情下极易穿仓，穿仓损失由保险基金承担。

## 2.2 现状

`MarginConfig { mmr_bp: i64 }` 单一比例。

## 2.3 数据模型

```rust
/// 一档保证金要求
pub struct Tier {
    /// 该档上限（名义价值），最后一档用 i64::MAX
    pub max_notional: Price,
    /// 该档的维持保证金率（万分之一）
    pub mmr_bp: i64,
    /// 该档的初始保证金率
    pub imr_bp: i64,
}

pub struct TierTable {
    /// 必须按 max_notional 升序；加载时校验
    pub tiers: Vec<Tier>,
}
```

## 2.4 关键设计：**阶梯式**而非**整体式**

这是最容易做错的地方。假设：0~1 万档 mmr=0.5%，1 万~10 万档 mmr=1%。

- ❌ **整体式**（错）：仓位 5 万 → 全按 1% 算 → 维持保证金 500
- ✅ **阶梯式**（对）：前 1 万按 0.5% + 后 4 万按 1% → 维持保证金 50 + 400 = 450

整体式会造成"跳档悬崖"：仓位从 9999 涨到 10001，维持保证金突然跳升一倍，
用户瞬间被强平。阶梯式是连续的、行业通行做法。

```text
mmr_for(notional):
    let mut mm = 0; let mut lower = 0;
    for tier in tiers:
        if notional <= lower: break
        let upper = min(notional, tier.max_notional);
        mm += (upper - lower) × tier.mmr_bp / 10000;
        lower = upper;
    return mm
```

## 2.5 验收标准

1. 分档边界连续：`notional = 10000` 与 `10001` 的维持保证金差 ≤ 1 单位；
2. 阶梯式与"分段手算"结果一致（用 3~5 组固定数据做表驱动测试）；
3. 表加载时校验 `max_notional` 严格升序，否则拒绝启动；
4. 强平判断改用 `equity < mmr_for(notional)` 而非比率比较。

# §3 F-03 条件单（止盈止损，P1）

## 3.1 业务背景

用户想"价格跌到 9000 就自动卖出止损"。这是散户最常用的功能之一，缺失会显著影响产品可用性。

## 3.2 现状

只有立即执行的命令，没有"等价格触发"的机制。

## 3.3 关键设计决策：**独立触发器，不进撮合簿**

条件单**不应该**挂进订单簿（它没有价格档位，也不参与撮合）。
正确做法是维护一个独立的触发器集合，**由行情（最新成交价或标记价格）驱动检查**。

```text
                 行情价格更新
                      │
                      ▼
        ┌─────────────────────────────┐
        │  TriggerBook（有序 BTreeMap） │
        │  BTreeMap<(trigger_price, id), TriggerOrder> │
        └──────────────┬──────────────┘
                       │ 命中触发条件
                       ▼
              生成普通 Command::Place
                       │
                       ▼
                  进入撮合引擎
```

用 `BTreeMap<(Price, u64), TriggerOrder>` 的原因：可以按价格有序扫描，
"价格从 10000 跌到 9000 时，所有 ≥9000 的止损卖单都要触发"，一次遍历即可，
不用全表扫描；`(Price, id)` 组合 key 保证同价触发顺序确定。

## 3.4 数据模型

```rust
pub enum TriggerKind {
    /// 价格 >= 触发价时触发（止盈买 / 止损平空）
    PriceAbove,
    /// 价格 <= 触发价时触发（止损卖 / 止盈平多）
    PriceBelow,
}

pub struct TriggerOrder {
    pub id: u64,
    pub user_id: u64,
    pub kind: TriggerKind,
    pub trigger_price: Price,
    /// 触发后要下的单（可以是市价，也可以带限价保护）
    pub order: OrderRequest,
    pub created_ts: u64,
}
```

## 3.5 算法步骤

```text
update_price(new_price):
  1. 若 new_price >= last_price（上涨）：
       从 TriggerBook 中取所有 kind==PriceAbove 且 trigger_price <= new_price 的单
  2. 若 new_price < last_price（下跌）：
       取所有 kind==PriceBelow 且 trigger_price >= new_price 的单
  3. 按 (trigger_price 优先序, id) 顺序逐个触发（顺序确定！）
  4. 每个触发 → 生成 Command::Place → 交给撮合引擎
  5. 从 TriggerBook 删除（一次性触发）
```

## 3.6 边界与坑

| 坑 | 处理 |
|---|---|
| **行情跳空**：价格从 10000 直接跳到 8000，中间 9000 的止损单怎么办 | 必须触发（不能因为"没经过 9000"就跳过），按跳空穿越处理：所有 `>=8000` 的止损卖单全部触发 |
| **触发顺序** | 跳空时多个触发，顺序影响成交结果 → 必须定义：**先按触发价从优到劣，同价按 id 升序** |
| **触发后无流动性** | 触发出来的市价单可能吃不到任何量 → 记录 `Canceled { Remainder }`，并向用户推送"触发但未成交"通知 |
| **止损变踩踏** | 同一价位大量止损单同时触发会砸出瀑布 → 产品层面应提示风险；技术层面可选"分批触发"或"仅允许限价止损" |
| **撤单** | 条件单也要能撤（`Command::CancelTrigger`） |
| **持久化** | TriggerBook 必须进快照，否则重启后止损单丢失（严重事故） |

## 3.7 验收标准

1. 价格穿越触发价 → 恰好在下一个价格更新时触发（不早不晚）；
2. 跳空穿越多个触发价 → 全部触发，且顺序符合"价格优先 + id 升序"；
3. 重启恢复后，未触发的条件单仍在，已触发的不会再触发；
4. 触发产生的订单在事件流里能被识别（事件增加 `Triggered { trigger_id, order_id }`）。

# §4 F-04 proptest 属性测试（P1）

## 4.1 为什么这是 P1

当前 28 个测试都是"手写场景"，覆盖的是**已知**情况。属性测试用机器生成
海量随机输入来验证**不变量**，能发现"手写想不到"的组合 bug。对一个涉及真金白银的
撮合引擎，这是性价比最高的质量投入。

## 4.2 要验证的五条不变量

| 不变量 | 形式化表述 | 说明 |
|---|---|---|
| I1 盘口不交叉 | `best_bid < best_ask` 恒成立 | 撮合正确性的基本标志；若交叉说明有该撮合没撮合 |
| I2 数量守恒 | 每笔 Trade 的 `maker.remaining + taker.remaining` 总量 = 命令总量 | 不能凭空创造或销毁数量 |
| I3 余额非负 | 任何时刻所有订单数量 ≥ 0 | 负数量意味着逻辑穿透 |
| I4 重放一致 | 同输入两次执行 → 事件序列完全相同 | 确定性 |
| I5 快照等价 | `snapshot → restore` 后盘口与恢复前完全一致 | 持久化正确性 |
| I6 索引一致 | 每个挂单都在 index 中，index 中每个 id 都在簿中 | 防止撤单索引与簿不同步 |

## 4.3 实现骨架

```rust
use proptest::prelude::*;

fn arb_command() -> impl Strategy<Value = Command> {
    (1u64..5, any::<bool>(), 9_000i64..11_000, 1i64..100, any::<bool>())
        .prop_map(|(user, is_buy, price, qty, is_market)| { /* 构造 Command */ })
}

proptest! {
    #[test]
    fn 盘口永不交叉(cmds in prop::collection::vec(arb_command(), 1..500)) {
        let mut eng = MatchingEngine::new();
        for cmd in cmds {
            eng.process(cmd);
            let (bids, asks) = eng.depth(1);
            if let (Some(b), Some(a)) = (bids.first(), asks.first()) {
                prop_assert!(b.0 < a.0, "盘口交叉: bid={} ask={}", b.0, a.0);
            }
        }
    }
}
```

## 4.4 验收标准

1. 六条不变量各有独立测试，每条至少跑 256 个随机用例（proptest 默认）；
2. proptest 失败时能输出最小化复现输入（proptest 自带 shrink）；
3. 任何不变量失败都视为阻断性问题，不允许跳过。

# §5 F-05 逐仓 / 全仓保证金模式（P2）

## 5.1 两者的区别（用例子讲）

- **全仓（Cross）**：账户所有资金共用一个保证金池。A 交易对亏了，可以用 B 交易对的盈利顶上，
  抗单能力强，但一个仓位爆仓可能拖累全部资金。
- **逐仓（Isolated）**：每个仓位独立分配保证金。这个仓位最多亏掉它自己的保证金，
  不影响其他仓位。风险隔离，但抗单能力弱。

## 5.2 数据模型改动

```rust
pub enum MarginMode { Cross, Isolated }

pub struct Position {
    pub margin_mode: MarginMode,
    /// 逐仓模式下的独立保证金（全仓模式下此字段不参与计算）
    pub isolated_margin: Price,
    // ... 原有字段
}
```

## 5.3 关键计算差异

| 场景 | 全仓 | 逐仓 |
|---|---|---|
| 保证金率 | `账户总权益 / Σ所有名义价值` | `该仓位 (isolated_margin + pnl) / 该仓位名义价值` |
| 强平判断 | 整个账户统一判断 | 每个仓位独立判断 |
| 强平影响 | 可能连带清算多个仓位 | 只清算该仓位 |
| 盈亏可挪用 | 可以 | 不可以 |

## 5.4 边界与坑

- 逐仓仓位不能"加保证金"以外的资金调用（否则等同全仓）；
- 全仓模式下 `isolated_margin` 字段必须为 0，否则数据含义混乱；
- 切换模式必须**空仓**时进行（有仓位时切换会导致保证金归属不清）；
- 强平扫描顺序：逐仓仓位先扫（风险独立），全仓账户整体后扫。

## 5.5 验收标准

1. 逐仓：一个仓位爆仓后，同账户其他仓位与余额不受影响（可用测试断言余额不变）；
2. 全仓：同一账户一个仓位亏损可被另一仓位盈利抵消，不触发强平；
3. 有仓位时切换模式被拒绝；
4. 快照恢复后 `margin_mode` 与 `isolated_margin` 正确还原。

# §6 F-06 ADL 完整规则（P2）

## 6.1 现状的不足

当前实现是简化版：按"未实现盈亏降序 + user_id 升序"取仓位，用粗略的
`pnl / mark_price` 折算数量。真实 ADL 需要处理：

1. **跨用户净额**：不是按单个仓位减，而是按用户在该合约的净持仓排序；
2. **杠杆加权**：高杠杆盈利仓位优先级更高（因为他们占用的保证金少、收益率高）；
3. **按比例分摊**：缺口可能无法用整数仓位精确覆盖，需要按比例摊给多个用户；
4. **部分减仓**：一个用户可能只被减一部分，而不是整仓。

## 6.2 完整排序公式

```text
优先级分数 score = 未实现盈亏率 / 杠杆
  where 未实现盈亏率 = (pnl / margin)   ← 收益率，不是绝对盈亏
        杠杆        = notional / margin

score 越大 → 越优先被 ADL
tie-break：user_id 升序
```

含义：赚得比例最高、同时杠杆最高的人最先被减 —— 因为他们"用最少的钱赚了最多的钱"，
减他们的仓对市场冲击最小、对系统最公平。

## 6.3 分摊算法

```text
gap = 需要社会化的亏损
候选 = 按 score 降序排列的盈利仓位
for pos in 候选:
    if gap <= 0: break
    该仓位最大可贡献 = pos.pnl            // 最多减掉它赚的钱
    本次减仓贡献 = min(该仓位最大可贡献, gap)
    减仓数量 qty = 本次减仓贡献 / mark_price   （向上取整到最小单位）
    if qty > pos.size: qty = pos.size
    gap -= qty × mark_price
    记录 AdlRecord { user_id, qty, price: mark_price }
残余 gap（所有候选都不够）→ 记 bad_debt，进保险基金账（记负），并向运营告警
```

## 6.4 边界与坑

- **整数取整**：向上取整会导致"减多了"，多减的部分要退还（记 `refund`）；
- **候选耗尽**：市场单边极端行情下可能所有盈利仓位都不够 → 必须记录 `bad_debt` 并告警，
  不能悄悄吞掉；
- **ADL 与强平并发**：同一用户不能同时被强平与被 ADL（用一个"处理中"标记串行化）；
- **通知**：被 ADL 的用户必须收到通知（行业惯例，否则会引发投诉）。

## 6.5 验收标准

1. 缺口能被完全覆盖时，`Σ减仓贡献 == gap`（±取整误差）；
2. 缺口无法覆盖时，返回 `bad_debt > 0` 且保险基金账目记录对应负债；
3. 排序结果对同一输入稳定（同样的仓位数据跑两次顺序相同）；
4. 单个用户被 ADL 的数量不超过其持仓量。

# §7 F-07 报价保护 / 价格带（P2）

## 7.1 业务背景

防两类事故：

1. **乌龙指**：用户误输价格（把 10000 输成 100000），会瞬间吃掉整个卖盘；
2. **闪崩传导**：某交易对瞬间暴跌，套利机器人抽干流动性，引发连锁强平。

## 7.2 方案：限价带（Price Band）

```text
band = mark_price × (1 ± band_pct)
例如 band_pct = 5%：允许 9500 ~ 10500

规则（二选一，建议 B）：
A. 硬拒：超出价格带的订单直接 Rejected { PriceOutOfBand }
B. 限幅：超出价格带的订单被"夹"到边界价（更友好，减少用户挫败感）
```

## 7.3 关键细节

- 价格带基于**标记价格**而非最新成交价（否则同样可被插针操纵）；
- 价格带要**随标记价格滚动更新**，但更新频率需限流（如每 1 秒一次），避免抖动；
- 极端行情下可**临时扩大**价格带（否则所有订单都被拒，市场失去流动性）—— 需要与风控联动；
- 市价单同样受限（市价单的"隐含限价"用当前价格带边界）。

## 7.4 验收标准

1. 超带订单按配置的策略（拒单/限幅）处理，且事件里有明确原因；
2. 价格带边界由标记价格计算，标记价格不变时边界不变（确定性）；
3. 价格带配置热更新后，新订单立即生效、已挂订单不受影响。

# §8 F-08 做市商批量接口（P2）

## 8.1 业务背景

做市商每秒要撤几十单、下几十单。逐个调用有两个问题：

1. 网络往返成本高；
2. **原子性缺失**：撤 5 单下 5 单的过程中如果部分失败，报价会变成单边裸露（只买不卖），
   风险极大。

## 8.2 方案：批量命令 + 全或无

```rust
pub enum BatchCommand {
    /// 先全部撤单，再全部下单，整体原子
    ReplaceAll {
        cancel_order_ids: Vec<u64>,
        new_orders: Vec<OrderRequest>,
    },
    /// 只批量撤单
    CancelAll { order_ids: Vec<u64> },
}
```

## 8.3 原子性怎么保证

在**单线程撮合内**天然可以做到：

```text
1. 预检查：所有新订单参数合法？撤单目标都存在？
   —— 任一不满足 → 整批拒绝，不产生任何事件
2. 执行：按顺序撤单 → 下单
3. 由于是单线程 + 纯内存，中途不会被打断，天然原子
```

**关键提醒**：不要在"跨多个交易对"的批量上承诺原子性 —— 那需要分布式事务，
成本极高且收益有限。做市商可以接受"每个交易对内部原子"。

## 8.4 验收标准

1. 批次中任一订单非法 → 整批不产生任何状态变更（簿与 index 完全不变）；
2. 合法批次执行后，所有订单都在簿上且 index 一致；
3. 批量操作只产生一条 `BatchResult` 事件 + 内含逐单事件，便于审计；
4. 单批次数量有上限（如 200 条），防止单条消息阻塞撮合。

# §9 F-09 Maker Rebate / 手续费阶梯（P2）

## 9.1 业务背景

交易所手续费是分层级的：maker（挂单方）通常费率更低甚至返佣（rebate），
taker（主动方）费率高。费率还随用户 30 日交易量分档（VIP 等级）。

## 9.2 关键设计：**引擎只输出费率标识，不算钱**

重要架构判断：**撮合引擎不负责计算手续费金额**。

理由：
1. 费率依赖用户 VIP 等级、30 日交易量 —— 这些是账户侧数据，撮合引擎不该持有；
2. 计算手续费需要账户余额、是否需要扣币/扣U 的规则 —— 属于清算职责；
3. 引擎若算钱，就必须知道用户等级，会让"每交易对独立实例"的设计变复杂。

所以引擎只输出：

```rust
pub struct Trade {
    // ... 原有字段
    /// 该笔成交中 maker 是否享受返佣（由 VIP 等级与订单类型决定，引擎不判断）
    pub maker_fee_class: FeeClass,
}

pub enum FeeClass {
    Maker,   // 挂单方
    Taker,   // 主动方
}
```

清算侧再按 `(user_id, FeeClass, 30日交易量档位)` 查费率表算金额。

## 9.3 为什么不做在引擎里（给评审看的理由）

| 方案 | 问题 |
|---|---|
| 引擎内算手续费 | 需要注入用户等级表 → 引擎状态膨胀 → 快照变大 → 恢复变慢；每次费率调整都要改引擎 |
| 引擎输出 FeeClass，清算算钱 | 引擎保持纯粹；费率策略可独立热更新；试算/对账容易 |

## 9.4 验收标准

1. 每笔 Trade 事件带 `maker_fee_class` / `taker_fee_class`；
2. 引擎代码中不出现任何费率数值（grep 验证）；
3. 清算侧用固定费率表能算出与手算一致的金额（跨模块集成测试）。

# §10 F-10 冰山单随机化（P3）

## 10.1 问题

固定 `display_qty` 的冰山单会被算法识别：观察到某档一直被吃但数量总是补回同样值，
就能判断这里有冰山单，从而针对性挂单。

## 10.2 方案：确定性伪随机

**必须保持重放确定性**，所以不能用系统随机数。做法：

```text
display = base ± base × jitter_pct / 100
其中伪随机种子 = (order_id, refill_count, seq)
用简单的确定性哈希（如 splitmix64）生成
```

这样：
- 同一订单的回补序列在任何机器上都一样（可重放）；
- 但对外看不出固定规律。

## 10.3 验收标准

1. 相同 order_id 与 refill_count 必然得到相同 display（确定性）；
2. 相邻两次回补的 display 不完全相同（随机化生效）；
3. display 上下限受 `base` 约束，不会超总量。

# §11 F-11 指标埋点与诊断（P3）

## 11.1 需要哪些指标

| 类别 | 指标 | 用途 |
|---|---|---|
| 延迟 | 命令处理耗时 p50/p99/p999（直方图） | 发现性能回退与长尾 |
| 吞吐 | 每秒处理命令数、每秒事件数 | 容量规划 |
| 队列 | WAL 待刷盘量、Kafka 消费 lag | 发现背压 |
| 状态 | 订单簿档位数、挂单总数、冰山单占比 | 容量与业务洞察 |
| 恢复 | 启动恢复耗时、重放命令数、快照大小 | 灾备演练 |
| 错误 | 拒单数（按原因分）、panic 次数 | 质量监控 |

## 11.2 实现方式（不引重依赖）

```rust
/// 极简直方图：固定桶，无锁（单线程使用）
pub struct Histogram {
    buckets: [u64; 24],  // 2^n 纳秒桶
    total: u64,
}
impl Histogram {
    pub fn observe(&mut self, nanos: u64);
    pub fn percentile(&self, p: f64) -> u64;
}
```

导出方式：每 10 秒把指标打成一行 JSON 写 stderr 或本地文件，由采集器读取。
**不要**在撮合路径里做网络 IO。

## 11.3 验收标准

1. 埋点代码在撮合路径上的额外开销 < 50 ns（基准对比验证）；
2. 指标导出不阻塞撮合（异步/独立线程）；
3. p99 延迟可从指标反推出与 criterion 基准同量级。

# §12 F-12 优雅关闭（P3）

## 12.1 关闭顺序（顺序错了会丢数据）

```text
1. 停止接收新命令（关闭 Kafka 消费 / 拒绝 API）
2. 处理完当前在途命令（最多等待 N 秒，超时则强制）
3. 做最后一次快照
4. flush + fdatasync WAL
5. 提交 Kafka offset
6. 退出进程
```

**为什么快照要在 flush 之前**：快照记录 `last_seq`，必须保证该 seq 之前的数据已落盘。

## 12.2 边界

- 两次关闭信号（SIGINT 两次）= 立即退出（运维需要强制手段）；
- 关闭超时要有兜底：超时后记录一条 `unclean_shutdown` 指标，下次启动就会走完整重放；
- 关闭过程中不允许做快照之外的耗时操作。

## 12.3 验收标准

1. 正常关闭后重启：不重放任何 WAL 记录（因为已快照）；
2. 关闭被 kill -9 打断后重启：能完整恢复到 kill 前已确认的状态；
3. 关闭耗时 < 5 秒（10 万挂单规模）。

# §13 F-13 快照版本迁移 + WAL 冷归档（P3）

## 13.1 快照版本迁移

问题：`EngineSnapshot` 结构一旦改动（加字段），旧快照反序列化会失败 → 无法启动。

方案：

```rust
#[derive(Serialize, Deserialize)]
pub struct SnapshotEnvelope {
    /// 结构版本号，每次不兼容改动 +1
    pub version: u32,
    /// 原始快照（按版本用不同结构解析）
    pub payload: Vec<u8>,
}
```

加载逻辑：

```text
读 version
  ├── 当前版本 → 直接反序列化
  ├── 旧版本   → 用旧结构反序列化 → 迁移函数升级到当前结构
  └── 未来版本 → 拒绝启动（降级运行会写坏数据）
```

## 13.2 WAL 冷归档

问题：滚动段删除只保留最近几段，但如果要做"任意历史时点回放"（审计/复盘），
就需要历史数据。

方案：

```text
热段（当前写）→ 温段（已快照，保留 24h）→ 冷存（压缩后转对象存储）
冷存格式：段号 + 起止 seq + 字节数 + sha256，随归档清单一起存
```

## 13.3 验收标准

1. 用旧版本快照能成功启动并迁移（提供一份 v1 测试快照）；
2. 未来版本快照拒绝启动且给出清晰错误；
3. 冷归档可按 `(symbol, seq范围)` 精确找回；
4. 归档文件的 sha256 校验失败时拒绝用于回放。
