## 0. 先做三件事（10 分钟）

### 0.1 确认工具链

```bash
cargo --version     # 需要 Rust 1.75+（项目 Cargo.toml 里写了 rust-version）
```

没装的话去 https://rustup.rs 装。Windows 用户需要额外的 MSVC 构建工具，rustup 会提示。

### 0.2 跑一遍测试（这一步很重要）

```bash
cd matching-engine
cargo test
```

你应该看到 `28 passed`。**先看到绿色，你才有信心相信后面读的东西是对的。**

### 0.3 跑一遍 demo

```bash
cargo run --bin demo
```

输出大致是：

```text
--- cmd #4  Place(OrderRequest { user_id: 2, side: Buy, ..., price: Some(10100), qty: 8 }) ---
    Trade { maker_order_id: 1, maker_user_id: 1, taker_order_id: 4, taker_user_id: 2,
            price: 10100, qty: 8, taker_side: Buy }
    Placed { order_id: 4, remaining: 0 }
    DepthSnapshot { bids: [], asks: [(10150, 10)] }

=== 崩溃恢复 ===
快照覆盖到 seq = 5
重放产生 3 个事件
买盘: [(10050, 5)]
卖盘: []
```

先不用理解每个字段，只要注意一件事：**输出全是"事件"，没有"状态打印"**。
这就是这个系统的核心思想（后面会讲）。

## 1. 30 分钟速览：只读三个文件

如果时间很紧，只读这三个，顺序不能变：

| 顺序 | 文件 | 只读哪部分 | 你要获得什么 |
|---|---|---|---|
| 1 | `src/types.rs` | `Command`、`Event` 两个 enum | 知道系统"吃什么、吐什么" |
| 2 | `src/book.rs` | 结构体定义 + `insert` + `depth` | 知道数据"存在哪、长什么样" |
| 3 | `src/engine.rs` | `place()` 函数 | 知道"输入怎么变成输出" |

三个文件读完，你已经理解 80% 的撮合逻辑了。剩下的都是持久化和业务外围。

**为什么是这个顺序**：先看接口（输入输出），再看数据结构，最后看算法。
反过来读（先读算法）会很痛苦，因为你会不断往回翻"这个字段是什么"。

## 2. 完整阅读路线（四阶段，每阶段带自测题）

### 阶段一：数据与接口（约 30 分钟）

**读**：`src/types.rs`、`src/book.rs`

**核心概念**：

```text
命令（Command）   ：外部让引擎做的事（下单 / 撤单）
事件（Event）     ：引擎做完后对外宣告的事实（成交 / 挂上 / 拒绝 / 取消）
订单簿（OrderBook）：当前所有未成交订单，按价格分档、同价排队
```

**自测题**（答不上来就回去重读）：

1. `Price` 为什么是 `i64` 而不是 `f64`？（答案在 `types.rs` 的注释里）
2. `BidKey` 为什么要反转比较方向？如果不反转，买盘最优价会出现在哪？
3. `RestingOrder` 里的 `visible` 和 `hidden` 分别代表什么？为什么深度里只看得到 `visible`？

### 阶段二：撮合算法（约 40 分钟，最重要）

**读**：`src/engine.rs` 的 `place()` 函数

**读法建议**：先把 `place()` 的注释读完（顶部有"四个步骤"），再逐行看代码。
遇到 `let Some(x) = ... else { break }` 这种语法，查 §5 的语法表。

**核心问题**（带着问题读，效率高很多）：

- 为什么成交价用 `level_price`（挂单方的价格）而不是 taker 的限价？
- 为什么 `trade_qty` 要取 `min(remaining, front_visible)`？
- 队首吃完后，代码怎么区分"普通单出队"和"冰山单回补"？
- `Placed { remaining: 0 }` 是什么意思？为什么全成交了还要发一个 Placed 事件？

**自测题**：

1. 我挂卖单 100 手 @10100，然后别人市价买 30 手。写出这个过程产生的**完整事件序列**。
2. 如果我把 `validate` 里的 `req.qty <= 0` 改成 `< 0`，哪个测试会失败？为什么？

### 阶段三：持久化与恢复（约 40 分钟）

**读**：`src/runner.rs` → `src/wal.rs` → `src/snapshot.rs`

**这是最容易读不下去的部分**，所以先记住一句话：

> **引擎只会算，不会记；Runner 负责先记账（WAL）再让它算。**

**读的顺序**：

1. `runner.rs` 的 `apply()`：只有 20 行，看懂"先 append 再 process"的顺序；
2. `wal.rs` 的帧格式注释：`[长度][CRC][数据]`，理解为什么要长度和校验；
3. `runner.rs` 的 `recover()`：加载快照 → 跳过已覆盖的 seq → 重放剩下的；
4. `snapshot.rs`：为什么用 tmp + rename。

**自测题**：

1. 如果 `apply()` 里把"先 append 再 process"改成"先 process 再 append"，崩溃后会发生什么？
2. 快照里为什么要存 `last_seq`？如果删掉这个字段，恢复时会怎样？
3. WAL 里存的是"命令"还是"事件"？为什么？

### 阶段四：业务外围（按需读，约 40 分钟）

| 文件 | 什么时候需要读 |
|---|---|
| `src/router.rs` | 要支持多个交易对时 |
| `src/futures_types.rs` | 要做合约（盈亏、保证金）时 |
| `src/liquidation.rs` | 要做强平 / 保险基金 / ADL 时 |
| `src/wal_segments.rs` | 要处理"WAL 文件太大"时 |
| `src/kafka.rs` | 要接 Kafka 时（需 `--features kafka`） |

## 3. 一个完整的手工推演（把代码跑在脑子里）

这是最有效的学习方式：拿纸笔跟着推一遍，然后跑测试验证。

### 场景

```text
① 用户 A 挂限价卖单：10 手 @10100
② 用户 B 挂限价买单：4 手 @10100
③ 用户 A 撤掉剩下的卖单
```

### 逐条推演

**① A 挂卖单**

关键代码路径：`place()` → 校验通过 → 撮合循环发现**买盘为空**（`crossing_price` 返回 `None`）
→ 跳出循环 → 走"剩余挂簿"分支 → `book.insert()`

```text
事件：
  Placed { order_id: 1, remaining: 10 }
  DepthSnapshot { bids: [], asks: [(10100, 10)] }
```

> 注意：即使没有成交，也一定有一个 `Placed`。这是"每个订单恰好一个终态事件"的体现。

**② B 买 4 手**

关键代码路径：`place()` → 撮合循环 → `crossing_price` 返回 `10100`
→ 取队首（A 的卖单，visible=10）→ `trade_qty = min(4, 10) = 4`
→ 写 `Trade` 事件 → A 的 `visible` 变 6（>0，不出队）→ B 的 remaining=0 → 循环退出
→ 走"全成交"分支 → `Placed { remaining: 0 }`

```text
事件：
  Trade { maker_order_id: 1, maker_user_id: 1,
          taker_order_id: 2, taker_user_id: 2,
          price: 10100, qty: 4, taker_side: Buy }
  Placed { order_id: 2, remaining: 0 }
  DepthSnapshot { bids: [], asks: [(10100, 6)] }
```

> 关键点：成交价是 `10100`（**A 挂的价格**），不是 B 的限价。
> 如果 B 的限价是 10500，成交价仍然是 10100 —— 这就是"被动方定价"。

**③ A 撤单（order_id = 1）**

关键代码路径：`process()` → `cancel()` → 用 `index` 查到 `( Sell, 10100 )`
→ `book.remove_from_level()` 从队列里摘除 → 返回 `Canceled`

```text
事件：
  Canceled { order_id: 1, reason: Requested }
  DepthSnapshot { bids: [], asks: [] }
```

### 验证你的推演

打开 `tests/replay.rs`，找到 `部分成交与价格时间优先` 测试，
把你的推演和测试断言对比。**如果一致，说明你真的入门了。**

## 5. Rust 语法速查（本项目实际出现的）

| 语法 | 出现在哪 | 一句话解释 |
|---|---|---|
| `Option<T>` / `Some(x)` / `None` | `types.rs` 的 `price: Option<Price>` | "可能有值也可能没有"。`None` 表示"没有价格"（市价单） |
| `if let Some(x) = ...` | `runner.rs` | 如果有值就取出用，没有就跳过 |
| `let ... else { }` | `engine.rs` `place()` | 取出失败就提前结束，比嵌套 match 清爽 |
| `&self` / `&mut self` | 几乎所有方法 | 只读借用 / 可写借用。同一时刻只能有一个可写借用 → 天然单线程 |
| `#[derive(Debug, Clone, ...)]` | 所有结构体 | 让编译器自动生成"打印、复制、比较、序列化"的实现 |
| `.expect("理由")` | 多处 | "这里一定不会失败，万一失败请让程序崩溃并打印这条理由" |
| `match x { A => .., B => .. }` | 各处 | 分支匹配，**编译器强制穷举所有情况**（漏一个就编译不过） |
| `?` 运算符 | `wal.rs`、`runner.rs` | "如果出错就直接往外返回错误"，省掉一堆 if |
| `impl From<A> for B` | `router.rs` | 让 `A` 能自动转成 `B`，于是可以用 `?` 转换错误类型 |
| `usize` / `u64` / `i64` | 各处 | 无符号/有符号整数。索引用 `usize`，金额用 `i64` |
| `as i64` | 各处 | 类型转换（Rust 不会隐式转，必须显式写） |
| `Vec<T>` / `VecDeque<T>` | `book.rs` | 动态数组 / 双端队列 |
| `BTreeMap<K, V>` | `book.rs` | 有序字典（按 key 排序） |
| `serde` 的 derive | 所有类型 | 自动生成"结构体 ↔ 字节/JSON"的转换 |

> 完整语法讲解不在这里展开。遇到看不懂的语法，先查这张表，再查 Rust 官方书
> （https://kaisery.github.io/trpl-zh-cn/ 中文版）。

## 7. 动手练习（从易到难，做完就真会了）

### 练习 1 · 改一个参数（5 分钟）

把 `engine.rs` 的 `DEPTH_LEVELS` 从 10 改成 3，跑 `cargo test`。
观察：有没有测试失败？为什么？

> 提示：现有测试用的盘口档位都很少，所以不会失败。这说明**测试没覆盖"档位超过 10"的场景**——
> 这本身就是一个可以补的测试。

### 练习 2 · 加一个拒单原因（15 分钟）

需求：如果用户下单数量超过 1,000,000，拒绝并返回 `QtyTooLarge`。

改三处：

1. `types.rs` 的 `RejectReason` 加一个变体；
2. `engine.rs` 的 `validate()` 加判断；
3. `tests/replay.rs` 加一个测试。

> 你会立刻体会到：**Rust 的 `match` 穷举会强迫你把所有分支都处理掉**，
> 加了枚举变体后编译器会告诉你哪里漏了。

### 练习 3 · 让冰山单的可见量可以被查询（20 分钟）

现状：`depth()` 只返回可见量。需求：加一个 `depth_with_hidden()` 返回 `(可见, 隐藏)` 两列。

> 这是理解 `book.rs` 数据结构的最好练习。

### 练习 4 · 写一个"总量守恒"属性测试（40 分钟）

不用 proptest，手写也行：生成 100 条随机命令，统计
"所有 Trade 的 qty 之和 == 所有命令的 qty 之和 - 最终挂单剩余量之和"。

> 这条等式如果不成立，说明撮合在某处凭空创造或销毁了数量。
> 参考 `tests/replay.rs` 里的 `Lcg` 伪随机实现。

### 练习 5 · 模拟一次真实的崩溃（30 分钟）

1. 用 `Runner` 处理 100 条命令（`snapshot_every = 30`）；
2. 手动把 WAL 文件末尾追加几个随机字节（模拟半写帧）；
3. 用 `recover()` 恢复，验证盘口与"正常跑完 100 条"的结果一致。

> 这是最接近生产事故的练习。做完你会真正理解"为什么崩溃不会导致账不平"。

## 8. 常见困惑 FAQ

**Q：为什么全项目没有一个 `Mutex` / `Arc` / `async`？**

A：因为撮合是纯 CPU 计算，不需要并发。每个交易对一个实例、实例内单线程，
天然没有共享状态。async 只出现在 Kafka 收发（IO 边界）。

**Q：为什么用 `BTreeMap` 而不用 `HashMap`？**

A：`BTreeMap` 有序（取最优价 = 取第一个），且迭代顺序固定（重放确定性要求）。
`HashMap` 的迭代顺序每次运行可能不同，会破坏"同样输入 → 同样输出"。

**Q：为什么事件里要带 `user_id`，下游不是能查到吗？**

A：两个原因：① 省一次数据库查询；② 避免竞态——如果下游收到 Trade 时订单表还没写完，
按 order_id 反查会查不到。事件自带全部信息就不会有这个问题。

**Q：为什么不直接在引擎里记账（扣钱、加币）？**

A：因为"记账"要处理余额、冻结、手续费、对账，这些是清算系统的职责。
引擎只输出"发生了什么"，下游根据事件构建账本（事件溯源）。职责分开后，
引擎可以保持极简和极快。

**Q：为什么 `expect` 和 `panic` 能用？不是说生产代码不能 panic 吗？**

A：区别在"谁能触发"：
- 用户输入非法 → 返回 `Event::Rejected`（用户错误，不能 panic）；
- 内部不变量破坏（index 与订单簿不一致）→ panic（说明代码有 bug，继续跑会算错账，
  不如立刻崩溃让人发现）。
完整的策略见 `docs/01` §11。

**Q：为什么快照要先 flush WAL 再写？**

A：快照会记录 `last_seq`。如果快照先写成功、但 WAL 里对应的数据还在缓冲区没落盘，
那么"快照声称覆盖到 100，实际 WAL 只有 80 条"——恢复时就会丢掉 20 条，
而且**没人会发现**。顺序反过来（先 flush 再写快照）就永远安全。

**Q：读代码时发现注释和代码不一致怎么办？**

A：**以代码为准，然后立刻修注释**。这个项目所有注释都要求"能说出为什么"，
注释失效比没有注释更危险。

## 10. 术语速查（读代码时随时回来查）

| 术语 | 一句话 |
|---|---|
| maker / taker | 挂单等成交的人 / 主动吃掉挂单的人 |
| 价格时间优先 | 先比价格，同价先到先得 |
| 订单簿 | 所有未成交订单的有序集合 |
| 深度（depth） | 盘口各价格档的挂单数量汇总 |
| 冰山单 | 只显示一部分数量的挂单，吃完自动回补 |
| STP | 自成交防护：不允许自己吃自己的单 |
| GTC / IOC / FOK | 一直有效 / 立即成交否则取消 / 全成或全不成 |
| PostOnly | 只允许挂单，会立即成交就拒绝 |
| WAL | 写前日志：先记"要做什么"，再真正做 |
| 快照 | 某一时刻的完整状态，用于加速恢复 |
| 重放 | 按日志顺序重新执行命令，得到相同状态 |
| 事件溯源 | 事件是唯一真相，状态由重放推导 |
| 保证金 | 开合约押的钱 |
| 维持保证金率 | 低于它就要被强平 |
| 标记价格 | 计算盈亏用的"公允价"，防插针 |
| 穿仓 | 亏损超过全部保证金 |
| 保险基金 | 穿仓时垫付的公共资金池 |
| ADL | 从盈利对手方强制减仓分摊亏损 |

## 11. 一页速记（贴在显示器旁边）

```text
1. 输入是 Command，输出是 Vec<Event>，引擎只做"转换"。
2. 撮合 = 够得着 → 取队首 → 取最小值成交 → 处理队首。
3. 成交价永远是 maker 的价格。
4. 每个 order_id 恰好一个终态事件（Placed / Canceled / Rejected）。
```
