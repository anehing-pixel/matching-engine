# 08 · 快照与恢复设计

> 本文档讲清楚两件事：**内存状态快照（`EngineSnapshot`）** 与 **WAL（含滚动分段）** 各自的流程与设计方案，
> 以及二者如何配合完成崩溃恢复。读完后应能回答：为什么要有两种"存档"、它们各解决什么问题、
> 恢复时谁先谁后、以及那个曾导致重复重放的 `seq` 接续红线。

---

## 0 · 一句话定位

```
WAL  = 增量日志（"我按了哪些键"）—— 只记命令，不拷内存，append-only
快照 = 状态检查点（"某一局的存档"）—— 全量克隆引擎内存，落盘为一份完整状态

恢复 = 加载最近快照（状态源）  +  重放快照点之后的 WAL（增量源）
```

⚠️ **两者是独立的两条持久化支柱，互不读写**（详见 `09-业务流程总览.md §⑦‑1`）：
- 快照的副本**来源是引擎自身状态**，不是从 WAL 拷页；
- WAL 只记录命令流，不知道引擎长什么样。

---

## 1 · 内存状态快照（EngineSnapshot）

### 1.1 为什么需要它

WAL 是 append-only 命令日志。如果**只有 WAL**，崩溃恢复就得从头重放**全部**命令——跑一年可能几百 GB、上亿条，
重启要读一整遍，慢到不可用。

快照把"重放起点"从"文件开头"前移到"最近一次存档时刻"：恢复时只重放**快照之后**那一小段 WAL，
从而把恢复时间从 O(全量历史) 压到 O(两次快照之间的增量)。

### 1.2 触发时机（两种）

| 触发 | 代码位置 | 说明 |
|---|---|---|
| **定量触发**：累计命令数达到 `snapshot_every` | `runner.rs:238 take_snapshot` 由 `apply` 内 `cmds_since_snapshot` 计数器驱动（`runner.rs` 的 `apply` 末尾） | 生产主线，内联、同步、STW |
| **优雅关闭触发**：`graceful_shutdown()` | `runner.rs:228-231` | 收摊前最后一次 `take_snapshot`，内部已含 `wal.flush()` |

### 1.3 快照里存什么

`EngineSnapshot`（`snapshot.rs:39`）是引擎全量状态的逐字段镜像：

| 字段 | 含义 | 恢复时作用 |
|---|---|---|
| `last_seq` | 本快照覆盖到的最后一条 WAL 序号 | 重放时跳过 `seq <= last_seq` |
| `next_order_id` | 下一个订单号 | 续编订单 id，避免重复 |
| `book` | 订单簿（`BTreeMap`+`VecDeque`，已实现 serde） | 恢复盘口 |
| `index` | 撤单索引，以 `Vec<(u64,(Side,Price))>` 形式序列化 | 恢复时重建 `HashMap`（仅点查，不影响确定性） |
| `stp_mode` / `price_band` / `mark_price` / `iceberg_jitter_bp` | 引擎级配置与最近标记价 | 随状态一起恢复，避免重启后保护/配置失效 |

### 1.4 快照流程（STW 全量 clone）

```text
take_snapshot():
  1. wal.flush()                ← 前提：last_seq 之前的 WAL 必须先落盘
  2. engine.snapshot(self.seq)  ← 对引擎当前内存做全量 Clone（含 book 深拷贝）
  3. save_snapshot(dir, snap)   ← 原子写入磁盘（见 1.5）
  4. purge_below(当前段号)      ← 滚动模式下删除快照之前的旧 WAL 段，回收磁盘
  5. cmds_since_snapshot = 0
```

⚠️ **第 2 步是同步阻塞的 STW（Stop-The-World）**：主线程当场把引擎状态整份克隆、序列化、落盘，期间该 symbol 整条流水线冻结。
实测代价（见 `07-内存与容量规划.md`）：**百万挂单约 1.4s 冻结、内存峰值冲到 2.59×**。这是当初选 STW 而非双缓冲/后台写的已知代价（方案选型见 §4）。

### 1.5 原子落盘（防半份快照）

`save_snapshot`（`snapshot.rs:125`）不是直接写 `snapshot.bin`，而是：

```text
先写 snapshot.bin.tmp  →  再 fs::rename(tmp → snapshot.bin)
```

`rename` 在同级目录内是原子操作，保证**任意时刻崩溃都不会留下半份快照**——要么看到完整的旧快照，要么看到完整的新快照。

### 1.6 版本信封与迁移（为什么不直接序列化结构体）

如果直接 `bincode::serialize(&EngineSnapshot)`，一旦结构体加字段，旧快照就再也读不出——线上表现为"升级后起不来"。

所以磁盘上存的是**信封**（`snapshot.rs:59`）：

```text
┌─────────────┬──────────────────────────────┐
│ version:u32 │ payload: Vec<u8>（各版本自定义） │
└─────────────┴──────────────────────────────┘
```

读取时（`load_snapshot`，`snapshot.rs:145`）先看 version：

- 等于当前版本（`CURRENT_VERSION = 2`）→ 按当前结构解析；
- 旧版本（v1）→ 按旧结构解析，再用 `migrate_v1` 升级（新增字段给默认值，如价格带关闭、无标记价）；
- **比程序还新** → 明确报错，**绝不允许降级运行**（降级会写坏数据）。

兼容三种文件：当前信封、旧版信封、更早的裸 v1 结构（无信封）。

## 2 · WAL（命令日志）与滚动分段

### 2.1 它是什么（再次强调：不是快照）

WAL = 顺序追加的命令流，帧格式（`wal.rs:38`）：

```text
[ u32 数据长度(小端) ][ u32 CRC32(小端) ][ 数据本体(bincode 序列化的 WalRecord) ]
```

- 只记**输入（命令）**不记输出（事件）——确定性引擎重放输入必得相同结果；
- 命令在执行**之前**先落盘，崩溃后重放即可恢复；
- 长度头让我们能"按帧跳读"；CRC 让我们能发现半写帧 / 磁盘位翻转，当作截断点处理。

### 2.2 为什么要"分段"（RollingWal）

单个 WAL 文件会无限增长：跑一年可能几百 GB，既占磁盘又拖慢恢复（每次重启都要从头读）。

`RollingWal`（`wal_segments.rs:32`）的方案：

- 写到一个段（`wal-000001`），超过 `max_segment_bytes` 就切下一个段（`wal-000002` …）；
- **快照做完后，快照之前的所有旧段都可以删掉**——因为快照已包含那时之前的全部状态，旧段再也没人需要（`runner.rs:247-248` 调 `purge_below`）。

### 2.3 崩溃截断修复（repair_truncate）

崩溃可能让最后一个段留下"半写的帧"。`open()` 时调用 `wal::repair_truncate`（`wal.rs`）
把段截回到最后一个**完好帧**（`read_frame` 遇到长度头截断或 CRC 不匹配就返回 `Ok(None)` 视为迭代结束），
保证后续追加不会写在一个坏尾巴后面。

### 2.4 段回收（purge_below）

`RollingWal::purge_below(keep_from)`（`wal_segments.rs:99`）：删除编号**严格小于** `keep_from` 且**不是当前段**的旧段。
保守起见永远保留当前正在写的段，避免删到正在 append 的文件。

### 2.5 两种模式

| 模式 | 文件形态 | 恢复读取 |
|---|---|---|
| `WalMode::Single` | 单个 `wal_path` 文件 | `read_all::<WalRecord>` |
| `WalMode::Rolling` | `wal_path` 目录下的分段 `wal-NNNNNN` | `read_all_segments::<WalRecord>`（按段号升序拼接） |

## 3 · 恢复流程（快照 + WAL 重放配合）

`recover`（`runner.rs:269`）是恢复的总入口。流程：

```mermaid
flowchart TD
    A[recover 启动] --> B{load_snapshot 有快照?}
    B -- 有 --> C[取 snapshot_seq = s.last_seq<br/>MatchingEngine::from_snapshot]
    B -- 无 --> D[新建空引擎<br/>snapshot_seq = 0]
    C --> E
    D --> E[read_all / read_all_segments<br/>读取全部 WAL 记录]
    E --> F[遍历全部记录取 wal_max_seq<br/>= max(各 rec.seq)]
    F --> G{逐条 rec.seq > snapshot_seq?}
    G -- 否 已含于快照 --> G
    G -- 是 --> H[engine.process(rec.command)<br/>重放]
    H --> I[RecoveryResult<br/>engine + wal_max_seq]
    I --> J[Runner::open 用 seq = wal_max_seq<br/>续编新命令]
```

关键点：

1. **先加载快照（状态源），再读 WAL（增量源）**。
2. **重放只恢复状态，不向 Kafka 等下游重复投递事件**——下游以事件幂等消费或通过 `seq` 对账；`replayed_events` 仅用于测试校验重放一致性。
3. **`seq` 接续红线（见 §3.1）**。

### 3.1 ⚠️ `seq` 必须接续到 `wal_max_seq`（真实缺陷，已修复）

恢复时新命令的编号**不能**续在 `snapshot_seq`，而必须续到 WAL 里出现的**最大序号 `wal_max_seq`**。

**为什么**（曾发生的 bug）：
1. 快照 `last_seq=5`，WAL 里还有 `seq 6..15` 共 10 条没被快照覆盖；
2. 崩溃恢复：重放 `6..15`，此时若把 `seq` 续在 5，新命令会得到 6、7、8……；
3. WAL 变成 `[1..15, 6, 7, 8]`，同一份日志里出现两套同号记录；
4. 此时若再做一次快照（`last_seq=8`），下次恢复会跳过 `seq<=8`，但 `9..15` 会被**再重放一次**——它们其实已在那份快照里 → **订单重复**。

修复（`runner.rs:284-299`）：`wal_max_seq` 遍历**全部**记录取最大值（而非只看被重放部分），`Runner::open` 用它续编。

## 4 · 设计方案选型（为什么是 STW 而非其他）

快照有四类经典方案，本项目选了**第 1 类（STW 全量 clone）**：

| 方案 | 机制 | 优点 | 缺点 | 本项目的结论 |
|---|---|---|---|---|
| **① STW 全量 clone**（采用） | 主线程内联、当场把引擎整份克隆+落盘 | 实现最简单、恢复确定性最强、无并发坑 | 触发那一条命令冻结流水线（百万单 ~1.4s、峰值 2.59×） | ✅ 选它，换简单与确定性 |
| ② fork + COW | 父进程 fork 子进程，子进程落盘、父进程继续 | 几乎零阻塞 | **Windows 无 `fork`**；Rust 多线程程序 `fork` 极度危险（只复制调用线程，其他线程锁状态不一致） | ❌ 排除 |
| ③ 双缓冲 | 引擎维护两份状态，后台线程落其中一份 | 阻塞小 | "快照途中又来新命令"需并发处理，复杂度陡增；升级路径 | ❌ 暂缓，留作升级路径 |
| ④ 持久化结构 | 订单簿直接以可持久化结构组织，免全量拷 | 增量落盘 | 引入 GC 压力、结构僵化 | ❌ 过度设计 |

**取舍逻辑**：撮合引擎最稀缺的是"恢复结果逐字节确定"。方案 ① 用"卡一下"换"实现简单 + 恢复确定"，在可接受范围内。
若要压低尾延迟尖峰，唯一正路是把快照挪到后台线程（方案 ③），那又会引入快照并发问题——这是已明确的**升级路径**。

### 4.1 快照写盘的三种代价档位 ↔ 本项目的选择

把"STW 快照写盘"按开销从低到高拆成三档，并对照 `save_snapshot`（`snapshot.rs:125-137`）的实际代码，本项目落在**第 2 档**：

| 档位 | 机制 | 阻塞量级 | 本项目是否采用 | 代码证据 |
|---|---|---|---|---|
| **① 切指针 / COW（近乎零拷贝）** | 双缓冲或 fork+COW：只翻转指针或写时复制，不真正拷贝内存、不（立即）写文件 | 毫秒级 | ❌ **排除** | 同 §4 方案 ②③ 的并发/平台原因（Windows 无 `fork`、Rust 多线程 `fork` 危险、双缓冲要处理"快照途中又来新命令"） |
| **② 单线程同步克隆 + 序列化 + 写文件（不 fsync 快照）** | `engine.snapshot()` 全量 Clone → `bincode` 序列化 → `fs::write` 进页缓存 → `rename` 原子替换 | 几百毫秒~几秒（∝ 状态大小） | ✅ **采用** | `snapshot.rs:81`（`book.clone()` 等）+ `snapshot.rs:127-136`（`bincode::serialize` + `fs::write` + `fs::rename`，**无 `sync_data`/`fsync`**） |
| **③ ② + `fsync` 整个快照文件** | 在 ② 基础上显式 `fdatasync` 快照文件，等磁盘 ACK | 秒级甚至更久（数据越大越慢） | ❌ **刻意不做** | `save_snapshot` 里只有 `fs::write` + `fs::rename`，没有 `sync_data`；`take_snapshot` 中的 `wal.flush()` 刷的是 **WAL** 不是快照 |

**你描述里的"序列化"在我们代码里其实是两步走**（这正是 STW 1.4s/百万单的来源）：

1. **`engine.snapshot()`（`snapshot.rs:81`）**：纯内存 `self.book.clone()` + 索引 `collect` 成 `Vec`，**不碰磁盘**，但此刻引擎存在两份 → 即 §1.4 的 **2.59× 内存峰值**；
2. **`save_snapshot`（`snapshot.rs:125`）**：把那份克隆体 `bincode::serialize`（再遍历一遍）+ `fs::write` 进临时文件 + `fs::rename` 原子替换。

所以"遍历整个内存状态"被算了两次（clone 一遍、serialize 一遍），状态越大越慢，与第 ② 档的"几百毫秒~几秒"量级吻合。

**为什么不选 ①（最便宜但没用）**：那一档要靠 COW 或双缓冲才能"不拷内存就拿到快照"。COW 在我们的栈（Windows + 多线程 Rust）上不安全；双缓冲则引入"快照进行中又来新命令"的并发难题——当初就是为换**简单 + 确定性**才放弃它（见 §4 方案 ②③）。

**为什么不选 ③（最贵也最没必要）**：关键设计认知——**快照只是检查点优化，不是真相源，WAL 才是持久性兜底**。

- 即使断电把"最新那份快照"丢了（它只 `fs::write` 进页缓存、没 fsync），恢复时也只会**退回到上一份快照 + 多重放一段 WAL**，最多恢复慢一些，**不会丢数据**——因为该区间命令早已在 WAL（若 `sync_each=true` 则已 `fdatasync` 落盘）；
- 反过来给快照文件也来一次 `fsync`，等于每次快照额外冻**几百毫秒~秒级**等磁盘 ACK，换来的"快照本身断电不丢"却**不增加任何数据安全性**（WAL 已兜住）。纯亏。

> **结论**：正确做法是持久性压在 WAL 上（必要时 `sync_each=true` 每笔 `fdatasync`），快照走第 ② 档只保证"不写坏、原子替换"（tmp+rename），不额外 fsync。即——**fsync 的成本只该花在 WAL 上，不该花在快照上。**

## 5 · 阻塞代价与权衡（回顾）

| 环节 | 阻塞量级 | 是否可接受 | 条件 |
|---|---|---|---|
| 每笔 WAL（write/flush，不 fsync） | ~2.4µs | ✅ 完全可接受 | 任意规模 |
| 每笔 WAL（每笔 `fdatasync`） | ~287µs | ⚠️ 有条件可接受 | 单品种 ≤ 几千 TPS |
| 定量快照 STW（内联全量 clone） | ~1.4s / 百万单 | ❌ 仅为简单性妥协 | 要低尾延迟需改造（方案 ③） |

> 快照的代价是"1.4s 内该 symbol 所有新订单排队"，不是小到无所谓的尖峰。这层与 `03-运维手册.md §2.2` 的 `sync_each` 两档代价、以及 `07` 的内存峰值 2.59× 互相对应。
